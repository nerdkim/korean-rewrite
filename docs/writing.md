# 한국어 작성 원칙

`korean-rewrite` skill에 들어 있는 원칙과 그 근거를 모은 문서입니다. 원칙은 국립국어원 자료, 국어학과 번역학 연구, 국내외 회사들이 공개한 글쓰기 가이드, 소프트웨어 현지화 스타일 가이드, 법령과 기관 지침, 웹 보안 자료, 언어 model을 다룬 연구에서 가져왔습니다. 검사기가 규칙마다 오류로 막을지 경고로 알릴지는 [검사 규칙](rules.md)에서 정합니다.

출처는 문서 끝에 모았고 본문에 처음 나오는 순서로 번호를 붙였습니다. 본문에서는 출처를 `[번호]`로 표시하고 쪽, 표, 표제어, 답변 번호처럼 출처 안의 위치를 밝힐 때는 `[번호: 위치]`로 표시합니다. 출처가 주장하는 내용에는 출처 번호를 붙입니다. 출처에 없는 규칙은 본문에서 이 repository의 규칙이라고 밝힙니다. 인용문과 출처 제목은 원문 표기를 그대로 두므로 이 repository가 영어로 쓰는 IT 용어가 한글로 나오기도 합니다.

예문 가운데 출처 번호를 붙인 것은 그 자료의 원문입니다. 출처 번호가 없는 고칠 문장은 Claude가 이 repository나 이 도구를 설치한 프로젝트에서 실제로 쓴 문장이거나 이 repository가 만든 문장입니다. 어느 쪽인지는 예문 앞뒤에 적습니다. 출처 번호가 없는 고친 문장은 이 repository가 다듬은 것입니다. 다른 프로젝트에서 가져온 문장은 사람 이름과 사이트 주소를 바꿔 적었습니다.

## 처음부터 한국어로 쓰기

Microsoft 한국어 현지화 스타일 가이드는 문장과 문단, 페이지 전체의 의도를 이해한 뒤 직접 쓰듯이 다시 쓰라고 합니다. 그래야 한국 고객에게 더 알맞고 자연스러운 글이 된다고 합니다[1: 5쪽]. 국립국어원도 우리말다운 문장이 가장 자연스럽다며 외국어 번역투는 어순이나 문체가 자연스럽게 느껴지지 않을 수 있으니 삼가라고 합니다[2: 12쪽].

언어 model이 영어에 기대어 뜻을 처리한다는 연구도 여럿 있습니다. 다국어 model은 입력 언어와 관계없이 중간층에서 영어에 가까운 표현으로 뜻을 처리하는 경향이 있습니다[3][4]. Anthropic은 Claude 3.5 Haiku가 중간층에서는 여러 언어에 공통된 표현으로 뜻을 처리하고 출력할 때는 영어를 기본 언어처럼 다룬다고 봤습니다[5].
영어로 쓴 글을 옮기면 영어 구조가 남는다는 보고도 있습니다. Claude Sonnet 5에게 2019년 논문의 영어 초록 99편을 한국어로 옮기게 하자 `에 의해`가 든 초록이 13.1%였습니다. 실제 한국어 초록에서는 이 비율이 2019년 7.9%, 2026년 5.7%로 더 낮았습니다[6: 표 18].
이 repository는 Claude가 README에 쓴 다음 문장도 영어 문장 틀을 따른 예로 봅니다. 서술어 하나 앞에 대상, 장소, 상대, 횟수가 몰려 있습니다.

`같은 요청 열두 가지를 이 도구가 없는 프로젝트와 설치한 프로젝트에서 Claude Opus 5.5에 두 번씩 보냈습니다.`

그래서 output style과 skill에는 요청을 읽을 때부터 한국어로 생각하라는 지시가 들어 있습니다. 두 문서도 한국어로 썼습니다. 다만 이 도구는 Claude가 속으로 어떤 언어로 생각하는지 확인할 수 없습니다. 한국어로 생각하라고 지시하면 model이 중간층에서 영어에 덜 기댄다는 연구도 찾지 못했습니다.
지시문 언어를 바꿔 출력의 자연스러움을 비교한 한 연구는 중국어와 프랑스어를 다뤘습니다. 지시문을 영어로 쓰자 중국어 출력은 model에 상관없이 덜 자연스러워졌지만 프랑스어 출력은 model마다 결과가 달랐습니다[7]. 한국어로 같은 실험을 한 연구는 찾지 못했습니다.

언어 model에게 자기 번역을 다시 다듬게 하는 단계는 효과가 확인됐습니다. 자연스럽게 옮기라는 요구를 지시문에 추가했을 때는 직역 문체가 조건에 따라 줄기도 하고 늘기도 했습니다. 반면 GPT-3.5와 GPT-4에게 자기 번역을 다시 다듬게 하자 영어를 중국어로 옮길 때와 독일어를 영어로 옮길 때 모두 직역 문체가 줄었습니다. 직역 문체는 GPT-4가 영어를 중국어로 옮긴 번역에서 가장 많이 줄었습니다. 이 번역에서는 직역 문체가 글의 20%를 넘게 드러난 번역문이 전체의 43%에서 25%로 줄었습니다[8].
이 도구에서도 검사기가 오류를 찾으면 hook이 Claude에게 글을 다시 쓰게 합니다. 다만 이 연구는 검사기 없이 model에게 자기 번역 전체를 다듬게 했고 검사기가 찾은 오류를 고치게 하는 방식은 시험하지 않았습니다.

**한글이 많은 글은 작업 맥락이 없는 작성 agent에게 맡깁니다.** 사용자는 이 도구를 설치한 다른 환경에서 Claude가 쓴 문단 두 개를 보여 주며 말이 이상하다고 알려 왔습니다. 두 문단 모두 누가 무엇을 어디에서 하는지가 흐렸습니다. 사용자가 알려 왔을 때 검사기는 두 문단에서 오류도 경고도 찾지 못했습니다. 지금은 첫 문단의 `승인을 묻습니다`만 경고로 알립니다. 이 repository의 README를 다시 쓸 때는 Claude가 먼저 초안을 썼습니다. 그 초안에서도 `korean-reviewer` agent가 고칠 곳을 46건 찾았습니다. 이 repository는 글쓴이가 자기가 아는 맥락을 글에서 빠뜨려도 잘 알아채지 못한다고 봅니다.
그래서 이 도구는 파일, commit 메시지, PR과 issue에 올리는 글에 한글이 많으면 작업하던 Claude가 직접 쓰지 않게 합니다. 작업하던 Claude는 독자, 글 종류, 말투, 담을 사실을 메모로 넘기고 작업 맥락이 없는 작성 agent가 그 메모로 글을 씁니다. 작성 agent에게는 메모에 없는 사실을 지어내지 말고 빠졌다고 알리라고 지시해 두었습니다. 한글이 많은 글을 작성 agent에게 맡기는 것은 이 repository의 규칙입니다. 작성 agent에게 맡겼을 때 글이 나아지는지는 아직 평가로 확인하지 않았습니다.

**다 쓴 글은 검토 model이 따로 다시 읽습니다.** 사용자는 이 도구를 설치한 환경에서 Claude가 쓴 화면 문구 `항목 942개 가운데 최근 200개를 표시했습니다. 앞선 항목은 journal 원문에 있습니다.`를 보여 주며 `앞선 항목`이 어색하다고 알려 왔습니다. 앞서도 화면 문구 `로그인하신 계정과, 어떤 화면을 어떤 근거로 여실 수 있는지 보여 드립니다.`를 알려 왔고 `승인을 묻습니다`가 든 답변 문단도 알려 왔습니다. 이 문장들은 낱말 하나하나가 맞는 한국어라서 낱말 목록으로 찾는 검사기로는 찾기 어렵습니다. 사례마다 규칙을 추가해도 다음 사례는 막지 못합니다.
이 도구를 설치한 다른 프로젝트 두 곳의 transcript에서도 `앞선 기록:`과 `오늘(KST)보다 앞선 항목은`이 든 문서를 찾았습니다. 하나는 사용자와 대화하던 Claude가 썼고 하나는 Sonnet subagent가 썼습니다. 두 session에는 모두 skill을 부른 기록이 있었고 hook이 검사기로 검사했지만 문장 길이 경고만 나왔습니다. 사용자가 알려 준 세 문장은 검토 model마다 여섯 번 보냈고 이때는 0.4.1까지 쓰던 검토 지시를 썼습니다. 검토 model 가운데 Sonnet은 여섯 번 모두 세 문장을 어색하다고 지적했습니다. Claude가 쓴 글에도 Claude model이 따로 읽으면 어색하다고 지적할 문장이 남아 있습니다. Skill에는 다 쓴 글을 다시 읽으라고 적어 두었습니다. 그러나 Claude가 정말 다시 읽는지는 Claude 안에서 일어나는 일이라 hook이 확인할 수 없고 transcript에도 thinking 본문이 남지 않습니다.
그래서 이 도구에서는 hook이 다 쓴 글을 검토 model에게 따로 다시 읽힙니다. 다 쓴 글을 검토 model에게 다시 읽히는 것은 이 repository의 규칙입니다. Claude가 요청을 마치면 검토 hook이 Claude가 쓴 한국어를 검토 model에게 보냅니다. 파일과 commit 메시지에 대한 지적은 Claude Code가 Claude에게 전달해 작업을 이어 가게 합니다. 답변에 대한 지적은 다음 요청 때 hook이 Claude에게만 알립니다. 이 repository의 session에서도 검토 model은 Claude가 도구를 부르는 사이에 쓴 영어 문장 `Now how-it-works.md.`와 `Now the README.`를 찾아냈습니다. 한국어로 답하던 Claude가 영어 문장을 그대로 쓴 예입니다.

기본 검토 model은 Sonnet입니다. 세 model의 지적 횟수와 비용은 2026년 11월 6일에 측정했습니다. 측정에는 Claude Code 2.1.310과 현재 검토 지시를 썼습니다. 예문 18개를 묶음 3개로 나눠 model마다 묶음을 여섯 번씩 보냈습니다. Model마다 번역투 문장은 모두 48번, 자연스러운 문장은 모두 60번 보낸 셈입니다. 검토 지시에는 이 예문의 문장과 그 문장에서 고칠 표현을 예로 넣지 않았습니다. Sonnet과 Opus는 번역투 문장을 똑같이 34번 지적했고 자연스러운 문장은 둘 다 한 번도 잘못 지적하지 않았습니다. Haiku는 32번을 지적했지만 자연스러운 문장을 6번 잘못 지적했습니다. 묶음 하나에 드는 비용은 Sonnet이 Opus보다 적었습니다. 따라서 결과가 같은 두 model 가운데 Sonnet을 기본값으로 두었습니다.
검토 model도 놓칩니다. 이 측정에서 Sonnet은 사용자가 알려 준 `앞선 항목` 문장을 여섯 번 모두 지적했지만 `앞선 기록:`이 든 문장은 한 번도 지적하지 못했습니다. `오늘(KST)보다 앞선 항목은`이 든 문장도 여섯 번 가운데 세 번만 지적했습니다. 사용자가 알려 준 `앞선 항목`이 다시 나오는지도 시험했습니다. 이 도구를 설치한 빈 프로젝트에서 같은 종류의 화면 component를 만들게 하거나 영어 문구를 한국어로 옮기게 했습니다. Opus로 8번, Sonnet으로 3번 시험했고 Claude는 11번 모두 `이전 항목`처럼 자연스럽게 썼습니다. 사용자가 본 문장은 다른 컴퓨터의 session에서 나와서 어떤 조건에서 나왔는지는 확인하지 못했습니다.

## 내용 고르기

이 도구를 설치한 다른 프로젝트에서 Claude는 개인 웹사이트의 개인정보 처리방침을 쓰면서 첫 문단을 다음처럼 썼습니다.

`example.com은 홍길동의 개인 profile page이며 회원 가입과 입력 양식이 없습니다. 오류를 찾고 page를 어떻게 쓰는지 알아보려고 아래 두 도구로 방문 기록을 모읍니다. 시험용 사본인 dev.example.com도 같은 방식으로 기록합니다.`

사이트 주인은 이 문단에서 세 가지를 지적했습니다. 첫째, `시험용 사본`은 어색한 한국어입니다. 둘째, 공개하면 안 되는 개발 server 주소가 들어갔습니다. 셋째, 처리방침에서 아무도 궁금해하지 않는 사이트 주인 소개가 들어가 개인 정보가 드러났습니다.
이 문단은 같은 페이지에 있는 영어 문단과 내용 순서가 같습니다. Claude는 영어 문단의 `test copy`를 `시험용 사본`으로 옮겼고 `profile page`는 영어로 두었습니다. 사이트 주인이 알려 왔을 때 이 도구의 검사기는 이 문단에서 오류도 경고도 찾지 못했습니다. 지금 검사기는 `시험용`만 번역투일 수 있다고 경고합니다. `사본`과 `page`는 검사기 규칙에 없는 말입니다. 개발 server 주소와 사이트 주인 소개는 문장을 쓰기 전에 무엇을 쓸지 고르는 단계에서 생긴 문제라 검사기가 판단할 수 없습니다. 그래서 skill에는 문장을 쓰기 전에 독자와 쓸 내용을 정하는 절차가 들어 있습니다.

**독자와 목적부터 정합니다.** 국립국어원은 행정 문서를 쓰기 전에 읽을 사람이 누구인지 구체적으로 파악하고 문서를 쓰는 목적을 정하라고 합니다. 문서에 담을 내용은 독자에게 필요한 정보여야 하므로 내용을 계획할 때부터 독자가 무엇을 알아야 하는지 파악하라고 합니다[9: 36-37쪽]. 토스는 문서를 쓰는 사람이 읽는 사람 입장보다 자기가 말하고 싶은 내용을 중심으로 구조를 짜기 쉽다고 지적합니다. 정보 구조 만들기 페이지에서는 기술 문서가 주로 문제 해결, 학습, 참조에 쓰이므로 독자가 어떤 목표로 그 문서를 찾았을지 생각하며 쓰라고 합니다[10]. 카카오엔터프라이즈는 글이 모호해지는 문제가 대부분 읽을 사람이 누구인지 제대로 파악하지 못해서 생긴다고 봅니다[11].

**독자에게 필요한 내용만 고릅니다.** 국립국어원은 글 종류에 따라 먼저 확인해야 할 내용과 반드시 필요한 내용이 달라진다고 합니다. 무엇을 소개해 알려 주는 안내문은 읽는 사람이 궁금해하는 내용을 중심으로 쓰라고 합니다[12: 22-23쪽]. Google은 독자에게 필요하지만 독자가 아직 모르는 정보를 문서에 담으라고 합니다. 설명은 쓰는 사람이 아니라 독자가 궁금해하는 것을 풀어 줘야 한다고 합니다. 초고를 검토할 때는 문서 첫머리에 밝힌 범위를 다루는 데 보탬이 되지 않는 절을 지우라고 합니다[13]. Microsoft는 독자가 자신 있게 결정할 만큼만 알려 주라고 합니다[14].
대화, 설정 파일, 작업 메모에서 알게 된 사실을 글감으로만 보고 문장마다 독자에게 필요한지 따지는 것은 이 repository의 규칙입니다. 고르면서 뺀 내용을 설명하는 문단을 덧붙이지 않는 것도 이 repository의 규칙입니다.

**독자가 이해하는 데 필요한 설명은 채웁니다.** 2026년 11월 7일에 이 repository의 README에 실을 설치 전후 비교를 만들었습니다. 이때 주문 목록 API의 응답 시간을 줄인 메모를 주고 팀 기술 블로그에 올릴 짧은 글을 써 달라고 Claude에게 요청했습니다. 이 도구를 설치한 프로젝트의 첫 번째 답변은 443자였습니다. 이 답변은 메모의 다섯 가지를 문장으로 옮겼을 뿐 N+1 query가 왜 느린지와 고친 방법이 왜 빠른지는 설명하지 않았습니다. 이 도구가 없는 프로젝트의 첫 번째 답변은 1,404자였고 원인과 해결 방법을 설명했습니다. 사용자는 블로그 글로는 이 도구를 설치한 프로젝트의 답변이 더 못하다고 지적했습니다. 그때 skill은 요청에 없는 내용을 채우지 말라고 하면서 예시 코드를 그 예로 들었습니다. 문장마다 없어도 독자가 잃는 것이 없으면 지우라고도 했습니다. Claude가 이 두 지시를 설명에도 적용한 것으로 보입니다. Google 지침도 독자에게 필요하지만 독자가 아직 모르는 정보를 문서에 담으라고 합니다[13]. 그래서 skill은 지어내면 안 되는 사실과 독자에게 필요한 설명을 나눕니다. 지어내면 안 되는 사실은 메모에 없는 수치, 날짜, 사람, 실제 코드와 설정, 팀의 결정과 계획입니다. 이렇게 나누는 기준은 이 repository의 규칙입니다. Skill을 고친 뒤 11월 8일에 같은 요청을 다시 보내자 이 도구를 설치한 프로젝트의 첫 번째 답변은 1,439자였고 N+1 query가 왜 느린지와 Redis에 cache하면 왜 빨라지는지 설명했습니다. 이때 skill에서 독자가 이해하는 데 필요한 설명을 채우라는 지시에 붙인 예문은 환율과 판매량 사례였고 이 요청과 겹치지 않았습니다. 이 답변은 팀이 cache를 지우는 방법을 검토하고 있다고 쓰지 않았고 다음 글을 약속하지도 않았습니다. 이 결과는 README의 `설치 전후 비교`에 실었습니다.

**공개하는 글에는 내부 정보와 개인 정보를 넣지 않습니다.** OWASP 웹 보안 점검 가이드는 점검하는 사람이 검색 엔진으로 찾아볼 민감한 정보의 예로 공개하지 않은 개발, test, staging 사이트를 듭니다. DNS record와 certificate transparency log에서 개발, staging, test host를 찾아내는 방법도 다룹니다[15]. 공개하는 글에 개발 server 주소를 적으면 이렇게 찾아낼 필요도 없이 주소를 알려 주는 셈입니다.
MITRE의 CWE-200은 정보 노출의 한 유형으로 누구나 볼 수 있는 resource에 민감한 정보를 넣는 경우를 듭니다. 민감한 정보의 예로는 연락처 같은 개인 정보와 network 구성을 듭니다[16]. 한국인터넷진흥원도 웹 서비스에서 불필요한 정보가 드러나지 않게 하라고 합니다. 드러난 정보가 2차 공격에 쓰일 수 있기 때문입니다[17].
다만 CWE-200과 한국인터넷진흥원 자료는 페이지 소스, 주석, 오류 메시지처럼 프로그램이 내보내는 정보를 다룹니다. OWASP는 관리자와 주요 직원이 남긴 게시물과 이메일도 찾아볼 정보로 들지만 공개하는 글을 쓸 때 무엇을 빼야 하는지는 다루지 않습니다. 공개하는 글의 본문에도 같은 기준을 적용하는 것은 이 repository의 규칙입니다. 이 repository는 공개 repository이므로 CLAUDE.md에도 개인 설정, 비공개 프로젝트 이름, local 경로를 Git이 추적하는 파일에 넣지 말라고 적어 두었습니다.
사용자나 사이트 주인의 실명과 소개를 사용자가 넣으라고 하지 않았으면 쓰지 않는 것도 이 repository의 규칙입니다. 개인정보 보호법은 처리방침에 개인정보 보호책임자의 성명이나 담당 부서와 연락처를 넣으라고 정합니다[18]. 이런 법정 항목은 사용자가 준 값으로 채웁니다. Skill은 독자가 찾지 않는 곳에서 사이트 주인을 소개하는 문장을 쓰지 말라고 합니다.

**법령과 기관 지침이 항목을 정한 글은 그 항목 이름과 용어를 씁니다.** 개인정보 보호법 제30조 제1항과 시행령 제31조 제1항은 처리방침에 넣을 사항을 정합니다. 처리 목적, 처리 및 보유 기간, 제3자 제공, 처리 위탁, 정보주체의 권리와 행사 방법, 개인정보 보호책임자, 개인정보를 자동으로 수집하는 장치의 설치와 운영 및 거부, 처리하는 개인정보의 항목, 국외 이전이 여기에 듭니다. 표준 개인정보 보호지침 제18조 제1항은 이 사항을 명시적으로 구분하되 알기 쉬운 용어로 구체적이고 명확하게 쓰라고 합니다[18]. 개인정보보호위원회 작성지침은 이 조항을 근거로 전문용어에 쉬운 설명을 덧붙이라고 권합니다[19].
작성지침의 작성 예시는 개인정보를 받는 쪽을 `제공받는 자`, `수탁자`, `이전받는 자`로 부릅니다[19]. 앞의 예문이 나온 페이지에서 Claude는 영어 표 머리글 `Recipient`를 `받는 곳`으로 옮겼습니다. 법령과 지침이 정한 말이 있는 글에서 영어를 옮겨 새 말을 만들지 않고 정해진 말을 쓰는 것은 이 repository의 규칙입니다.

**두 언어로 쓰는 글은 언어마다 따로 씁니다.** 웨일스 정부의 두 언어 서비스 지침은 웨일스어 콘텐츠를 영어 콘텐츠의 번역에 그치게 하지 말고 영어와 나란히 쓰라고 합니다. 바로 다음 문장에서는 두 언어를 늘 나란히 쓰기는 어려울 수 있다고 덧붙입니다[20]. WordPress 번역 지침은 번역문이 영어 문장 구조를 따를 필요가 없다고 합니다. 원문이 전하는 생각을 옮기는 언어에서 자연스러운 문장으로 새로 쓰라고 합니다. 말투를 맞추려고 emoji처럼 원문에 없는 요소를 넣으면 뜻이 바뀔 수 있으니 되도록 피하라고도 합니다[21]. Mozilla는 뜻을 더하거나 빼지 말고 직역은 무슨 일이 있어도 피하라고 합니다[22].
그래서 skill은 Claude가 두 언어로 처음 쓰는 글에서 한국어 문단을 정한 내용으로 따로 쓰게 합니다. 사용자가 준 글을 옮길 때는 원문의 사실을 빼지 않고 원문에 없는 사실도 넣지 않습니다[22]. 독자를 위한 설명을 덧붙이지 않는 것은 이 repository의 규칙입니다. WordPress는 독자에게 더 맞게 고칠 재량도 인정합니다[21].

## 번역투

이 repository는 번역투를 금지합니다. 이 절은 번역투의 정의와 판단 기준을 밝히고 금지하는 번역투와 번역투로 보지 않는 정상 용법을 구분합니다.
국립국어원의 공공언어 자료도 번역투를 피하라고 합니다. 『한눈에 알아보는 공공언어 바로 쓰기』는 '외국어 번역투 삼가기'를, 『쉬운 공공언어 쓰기 길잡이』는 '번역투를 피한다'를, 『쉬운 공문서 쓰기 길잡이』는 '우리말다운 표현 쓰기'를 항목으로 둡니다[2: 12-13쪽][12: 20쪽][9: 13쪽]. 카카오엔터프라이즈는 기술 문서에서 피동형과 사동형 문장이 번역투의 느낌을 강하게 해 부자연스럽게 읽힐 수 있다고 봅니다[23]. 토스 가이드도 번역체 표현을 자연스럽게 고치라고 합니다[10].

### 정의

**번역투는 외국어 원문의 낱말, 문장 구조, 표현 방식을 그대로 따라 써서 원문의 흔적이 드러나는 표현입니다.** 외국어는 주로 영어와 일본어입니다. 같은 뜻의 자연스러운 한국어 표현이 있을 때만 번역투로 봅니다. 이 정의는 이 repository가 정한 것입니다.

김정우는 번역투를 "어떤 글에 원본(original text)이 아닌 번역(translated text)이라는 흔적이 일정하게 반복적으로 출현하는 텍스트상의 특성"으로 정의합니다[24: 61쪽]. 김한식은 시상식 사회자의 "신사 숙녀 여러분"처럼 번역의 흔적이 뚜렷한 말도 이미 정착했으면 번역투라고 부르지 않는다고 봅니다[25: 83쪽]. 류현주도 번역투가 시간이 흐르면서 "‘정상적인 “표준 언어”’로 정착되는 특성"이 있다고 지적합니다[26: 8쪽]. 이 repository는 김한식과 류현주의 견해, '판단 기준' 절에 적은 김정우의 등가 기준을 반영해 정의에 '같은 뜻의 자연스러운 한국어 표현이 있을 때'라는 조건을 두었습니다.

번역투는 대부분 문법 오류가 아닙니다. 국립국어원은 "번역 투의 문장을 비문으로 보지는 않습니다"라고 답했습니다[27: 331784번]. 사전과 어문 규범에 영어 투 표현을 따로 정한 규정도 없다고 밝혔습니다[27: 334318번]. 김순영은 영어 구문을 그대로 옮긴 문장을 "문법적으로나 의미면에서 틀렸다고는 할 수 없지만 원문의 구조를 그대로 상기해 낼 수 있는 어색한 번역투 문장"으로 평가합니다[28: 74쪽]. 조의연은 번역문의 특징을 목표 언어의 체계에서 벗어난 것이 아니라 비번역문과 규범이 달라서 나타난 것으로 봅니다[29: 159쪽].

말뭉치 연구에서도 번역투는 빈도의 차이로 드러납니다. 김정우는 번역문 100만 어절과 비번역문 100만 어절을 비교한 김혜영(2009)의 연구를 소개합니다. 이 연구에서 영한 번역문에는 비번역문보다 "‘만들다, 가지다, 의하다, 대하다’ 등의 동사"가 많이 쓰였고 "‘-에 의하여’를 행위자로 하는 피동 표현"이 두드러졌습니다[30: 56-57쪽]. 번역문에는 `그`, `이것`, `그것`, `것`, `-의`, `-으로부터`, `-어지다`도 많이 쓰였고 시간은 선어말 어미보다 `-고 있다` 같은 보조 용언으로 나타낸 경우가 많았습니다[30]. Skill에는 이 가운데 `것`, `의`, `그것`, `가지다`, `대하다`, `의하다`, `-고 있다`가 한 문단에 몰리면 번역투일 수 있다는 신호라고 적혀 있습니다.
독자가 번역투를 늘 어색하게 느끼는 것도 아닙니다. 오미형은 대학생 31명에게 번역투가 든 문장을 읽게 한 결과 학생들이 번역투라고 해서 가독성을 반드시 낮게 평가하지는 않았다고 보고합니다[31].

따라서 번역투 금지는 어문 규범이 아니라 이 repository가 정한 문체 규칙입니다. 검사기가 어떤 번역투를 오류로 막고 어떤 번역투를 경고로 알리는지는 규칙 문서(`docs/rules.md`)에서 정합니다.

### 판단 기준

**같은 뜻의 더 자연스러운 한국어 표현이 있으면 번역투로 보고 고칩니다.** 이 기준은 김정우의 등가 기준을 따른 것입니다. 김정우는 "번역투 표현은 원칙적으로 모국어에 등가 표현이 있는 경우에 극복의 대상이 되지만, 그렇지 않은 경우에는 수용의 대상이 될 수 있다"고 결론짓습니다[24: 79쪽]. 김정우는 번역투가 모국어의 "‘우연한 빈칸’(accidental gap)"을 채울 때에만 그 긍정적 측면을 인정합니다. 69쪽 각주에서는 "모국어에 해당 번역투 표현과 등가(역동적 등가 포함)인 표현이 있다면 이는 극복의 대상이 된다"고 덧붙입니다[24: 69쪽].

이 repository는 이 기준을 적용할 때 다음 세 가지 규칙을 따릅니다.

1. 고친 문장이 원래 문장과 뜻, 조건, 시제가 같을 때만 등가 표현으로 봅니다.
2. 표준국어대사전에 예문과 함께 오른 용법이고 명사 사이의 관계나 뜻을 밝히는 표현은 번역투로 보지 않습니다.
3. 번역투를 피하려고 명사를 나열하거나 뜻을 흐리지 않습니다.

두 번째 규칙은 국립국어원의 답변과 방향이 같습니다. 국립국어원은 `~ 통해`가 일본어식 표현에서 유래했는지는 확인할 수 없다고 답했습니다. 다만 일본어식 표현에서 유래한 말이라도 "국어에서 자리를 잡고 널리 쓰여 사전에 등재되어 있다면 사용하지 말아야 한다고 금지하기는 어렵습니다"라고 덧붙였습니다[27: 327672번].

첫 번째와 세 번째 규칙은 표현을 바꾸면 뜻이 바뀌거나 흐려질 수 있다는 자료에 근거합니다. 국립국어원은 `법에 의해 보호받다`는 근거를, `법으로 보호받다`는 수단을 나타내므로 두 표현은 뜻이 다르다고 설명합니다[27: 323830번]. 이재성의 연구에서 GPT-4는 "AI는 학생들의 학습을 지원하고 윤리적인 글쓰기 태도를 형성하는 데 기여한다"를 "AI는 학생들의 학습 지원, 윤리적 글쓰기 태도 형성에 기여한다"로 단순화하자고 제안했습니다. 이재성은 이 제안으로 "조사 생략으로 인한 문법적 어색함이 새롭게 발생"했다고 보고합니다[32: 199-200쪽]. 국립국어원은 `성중독 이해`, `성중독의 이해`, `성중독에 대한 이해` 순서로 이해의 대상이 분명해진다고 설명합니다[27: 328611번].

### 금지하는 번역투

**다음 표현은 같은 뜻의 자연스러운 한국어 표현이 있으므로 번역투로 보고 고칩니다.**

- **이중 피동.** 피동사나 `-되다`가 붙은 피동 동사에 `-어지다`를 다시 붙인 말입니다. `보여지다`는 `보이다`로, `결정되어지다`는 `결정되다`로, `고려되어지다`는 `고려되다`로 고칩니다. 국립국어원은 피동사 `보이다`에 `-어지다`를 결합한 `보여지다`를 이중 피동으로 봅니다[27: 329347번]. `마무리되어지다`도 일반적인 관점에서 이중 피동으로 보고[27: 305626번] `고려되어지다`는 `고려되다`로 쓰는 것이 적절하다고 답했습니다[27: 315118번]. 『쉬운 공문서 쓰기 길잡이』는 `프로그램이 마무리되어진다`를 `프로그램을 마무리한다`로 고칩니다[9: 13쪽]. 쿠버네티스 한글화 팀도 `-되어지다`를 `-되다`로 고칩니다[33]. Lee의 집계에서 `되어지다`가 든 한국어 학술지 초록의 비율은 표에 실린 모든 연도와 model 조건에서 0이었습니다[6: 표 18]. 국립국어원은 `밝혀지다`를 이중 피동으로 보기 어렵다고 답했습니다[27: 315483번].
- **행위자를 `~에 의해`로 붙인 피동문.** 사람이나 프로그램이 한 일을 피동으로 돌리고 행위자를 `~에 의해`로 붙인 문장입니다. `설정 값은 server에 의해 결정되어집니다`는 `server가 설정 값을 정합니다`로 고칩니다. 국립국어원은 영어 번역 투의 첫 예로 "어색한 피동 표현(~에 의해 ~되다)"을 들고 `조선은 태조 이성계에 의해 건국되었다.`를 `조선은 태조 이성계가 건국했다.`로 고칩니다[2: 12쪽]. 김정우는 "행위자를 표시하는 ‘-에 의해’라는 어구에 영어식 수동 구문의 구조가 그대로 드러나 있다"고 봅니다[24: 71쪽].
  다음 두 연구에서 기계 번역과 언어 model은 `에 의해`를 사람보다 많이 썼습니다. 영어 수동문의 by 구문을 피동으로 옮긴 번역 가운데 `의해`를 쓴 비율은 사람 번역 11.1%(9개 가운데 1개), 파파고 57.1%(21개 가운데 12개), Google 번역 36%(25개 가운데 9개)였습니다[34: 341쪽]. '처음부터 한국어로 쓰기' 절에 적은 대로 Claude Sonnet 5가 영어 초록을 옮긴 글에서도 `에 의해`가 든 초록의 비율이 실제 한국어 초록보다 높았습니다[6: 표 18].
  피동을 모두 능동으로 바꾸지는 않습니다. 김정우는 능동문으로 고치면 화제가 드러나지 않는 문장이 있다고 지적합니다[24: 70쪽]. 수동태 번역투를 능동문으로 고치는 방식을 두고는 "항상 그런 방식이 적용될 수 있는 것은 아니다"라고도 덧붙입니다[24: 71쪽]. 따라서 이 repository는 사람이 하는 일은 능동형으로 쓰고 시스템의 상태가 바뀌는 일은 `파일이 저장됩니다`처럼 `-되다`로 씁니다. 이 구분은 이 repository의 규칙입니다.
- **사물의 소유와 속성을 말하는 `가지다`.** `세 개의 component를 가지고 있습니다`는 `component가 세 개입니다`로 고칩니다. 김정우는 "사랑하는 처자를 가진 가장"에서 영어 소유 구문의 흔적을 보고 "사랑하는 처자가 있는 가장"으로 고칠 수 있다고 봅니다[24: 70쪽]. 김순영이 인용한 이근희(2005)의 예에서는 `그녀는 아름다운 목소리를 가지고 있다.`를 `그녀는 목소리가 아름답다.`로 고칩니다[28: 73쪽]. Microsoft도 `필요한 사용 권한을 가지고 있지 않을 수 있습니다`를 `필요한 권한이 없을 수 있습니다`로, `관계를 이미 갖고 있습니다`를 `관계를 이미 맺고 있습니다`로 고칩니다[1: 30-31쪽]. 쿠버네티스 한글화 팀은 `짧은 다리를 가진 돼지`를 `다리가 짧은 돼지`로 고칩니다[33]. 이근희는 과학 기사 번역 100건에서 `가지다`를 번역투로 164건 집계했습니다[35: 278쪽].
- **동작 명사에 붙은 `~을 통해`와 `~함에 있어`.** 동작을 명사로 바꾼 뒤 조사구를 붙인 표현입니다. `cache 초기화 진행을 통해 해결했습니다`는 `cache를 초기화하여 해결했습니다`로, `API를 설계함에 있어`는 `API를 설계할 때`로 고칩니다. 국립국어원은 `취업 박람회 개최 등을 통해`를 `취업 박람회를 개최하여`로 고치면서 "‘~을 통해’는 번역 투이므로 자연스러운 표현으로 바꾸어 준다"고 적습니다[2: 19쪽]. 『쉬운 공문서 쓰기 길잡이』는 `시설물에서 촬영함에 있어서`를 `시설물에서 촬영할 때`로 고칩니다[9: 13쪽]. 김정우는 `의사소통을 함에 있어`를 "‘의사소통을 할 때, 전혀 ~’처럼 절로 풀어주면 자연스러워진다"고 봅니다[24: 73쪽]. 이창수는 `increased public attention`처럼 동사를 형용사로 바꿔 명사를 꾸미는 영어 명사구를 그대로 옮기면 번역투가 된다고 봅니다. 그리고 번역자들이 이 명사구를 풀어 동사로 옮기는 방법을 가장 많이 택했다고 보고합니다[36].
  국립국어원의 해설은 `~을 통해`를 조건 없이 번역 투로 부릅니다[2: 19쪽]. 그러나 이 repository는 동작 명사에 붙은 `~을 통해`만 금지합니다. 경로와 매개를 뜻하는 `~을 통해`는 정상 용법에 해당합니다. 이 구분은 이 repository의 규칙입니다.
- **목적어 자리의 `~에 대해`.** `성능에 대해 개선했습니다`는 `성능을 개선했습니다`로 고칩니다. 표준국어대사전은 `대하다`를 "‘대한’, ‘대하여’ 꼴로 쓰여" 대상이나 상대로 삼는다는 뜻으로 풀이합니다[37: '대하다2']. 이 repository는 `개선하다`처럼 목적어를 받는 동사 앞에서는 대상을 목적어로 써야 문장 성분이 맞는다고 보고 이 표현을 금지합니다.
- **사람을 상대로 한 `~에 대하여`와 `~에 대한`.** `참석자들에 대하여 감사를 전합니다`는 `참석자들에게 감사를 전합니다`로 고칩니다. 국립국어원은 `직원들에 대하여`를 `직원들에게`로 고치며 "‘~에 대하여’는 영어 번역 투이다."라고 적습니다[2: 41쪽]. 같은 자료는 `참석자들에 대하여 감사를 전하면서`를 `참석자들에게 감사를 전하며`로 고치고[2: 53쪽] `종사자에 대한`을 `종사자에게`로 고칩니다[2: 63쪽]. 다른 견해도 있습니다. 국립국어원 온라인가나다는 `대통령께 대하여 경례`를 고치면서 "‘대통령에 대하여 경례’ 또는 ‘대통령께 경례’로 쓰는 것이 자연스럽습니다"라고 답했습니다[27: 327770번]. 이 repository는 『한눈에 알아보는 공공언어 바로 쓰기』를 따라 이 용법을 금지합니다.
- **수량 표현 뒤의 `-들`.** `모든 test들이 통과했습니다`는 `모든 test가 통과했습니다`로 고칩니다. 이근희는 맥락으로 단수와 복수를 알 수 있거나 수사로 수를 밝힌 경우에 "명사에 복수접미사 ‘-들’을 표기하지 않는 방법이 한국어 어법으로 적합하다"고 봅니다[35: 276쪽]. Microsoft는 복수를 나타내는 `들`을 생략하는 경우가 많고 생략해도 전체 의미에 영향이 없으며 문법적으로도 허용된다고 적습니다[1: 28쪽].
  그러나 `-들`이 뜻을 더하는 경우도 있습니다. 김정우는 "땅 위에 흩어진 조약돌들"에서 `-들`이 "‘여기 저기 흩어져 있는 모습’을 효과적으로 표현"한다고 봅니다[24: 72쪽]. 김순영은 국어의 `-들`이 "‘느낌’의 차이를 전달하는 역할"을 한다고 봅니다[28: 76쪽]. 따라서 이 repository는 `모든`, `여러` 같은 수량 표현 뒤에 붙은 `-들`만 금지합니다. 이 범위는 이 repository의 규칙입니다.
- **`~것이 가능하다`.** `설정하는 것이 가능합니다`는 `설정할 수 있습니다`로 고칩니다. 토스 가이드도 `데이터베이스 접속 설정 진행이 가능합니다`를 `데이터베이스에 접속하도록 설정할 수 있습니다`로 고칩니다[10]. `~것이 가능하다`를 금지하는 것은 이 repository의 규칙입니다.
- **사람이 할 일을 하는 사물.** `이 기능은 사용자가 data를 내보내는 것을 허용합니다`는 `이 기능을 사용하면 data를 내보낼 수 있습니다`로 고칩니다. 국립국어원은 "스스로 움직이지 않는 사물이나 추상적 대상이 능동적 행위의 주어로 나오는 문장"을 영어 번역 투로 봅니다. 예로 `이 설문조사 결과는 청소년 언어 개선책을 시급히 마련해야 한다는 점을 말해 주고 있다.`를 `청소년 언어 개선책을 시급히 마련해야 한다는 점을 이 설문조사 결과에서 알 수 있다.`로 고칩니다[2: 13쪽]. 강주헌은 우리말 `허락하다`의 주어로는 사람만 올 수 있지만 영어 `permit`의 주어로는 사물도 올 수 있다고 설명합니다. 그래서 `Cash machines permit us to withdraw money at any time.`을 `현금 인출기 덕분에 우리는 돈을 어느 때나 인출할 수 있다.`로 옮깁니다[38]. 김도훈도 무생물 주어를 영한 번역투의 한 유형으로 다룹니다[39].
- **`~하지 않으면 안 된다`.** `설정 파일을 먼저 수정하지 않으면 안 됩니다`는 `설정 파일을 먼저 수정해야 합니다`로 고칩니다. 이 항목은 이 repository의 규칙입니다.
- **영어 복수형.** `여러 PRs를 merge했습니다`는 `PR 여러 개를 merge했습니다`로 고칩니다. Microsoft는 복수를 뜻하는 s가 붙은 영어 약어를 한국어로 옮길 때 s를 뺀다고 정하고 `몇몇 IFSs`를 `몇몇 IFS`로 고칩니다[1: 20쪽].
- **영어 낱말과 표현을 하나씩 옮긴 말.** `더하다`(add), `재다`(measure), `코드 밖에서 만든`(outside of code), `응답 모양`(shape), `CI가 돕니다`(run), `비멱등`(non-idempotent), `미추적`(untracked), 제목 `## 왜`(Why)가 여기에 듭니다. 이 말들의 근거는 이 문서의 '낱말' 절에 있고 고친 예는 skill의 '고칠 표현' 절에 있습니다. 다음 세 가지는 이 repository의 규칙입니다. `세다`(count)는 문맥에 따라 `집계하다`, `계산하다`, `확인하다`로 씁니다. Server나 환경을 갖추는 `세우다`(set up)는 `구성하다`나 `실행하다`로 씁니다. `결정을 만들다`(make a decision)는 `결정을 내리다`로 씁니다. 검사기는 `개수`, `글자`, `항목` 같은 말이 목적어인 `세다`를 `literal-verb` 경고로 알립니다. 영어 낱말이나 `서버`, `환경`, `시스템`이 목적어인 `세우다`와 `결정을 만들다`도 같은 경고로 알립니다.

### 번역투가 아닌 정상 용법

**이 repository는 다음 표현을 번역투로 보지 않습니다.** 모두 표준국어대사전에 오른 용법이거나 국립국어원이 오류가 아니라고 답한 표현입니다. 이 표현을 피하려고 명사를 나열하거나 뜻을 흐리지 않습니다. 이 목록은 이 repository가 정했으며 항목마다 근거를 붙였습니다.

- **명사를 꾸며 대상을 밝히는 `~에 대한`.** `요청에 대한 응답`, `기존 model ID에 대한 요청`, `응급 의료에 대한 관심`이 그런 예입니다. 표준국어대사전은 `대하다`의 뜻을 "【…에】 ((‘대한’, ‘대하여’ 꼴로 쓰여)) 대상이나 상대로 삼다."로 풀이합니다. 예문은 "전통문화에 대한 관심."과 "강력 사건에 대한 대책."입니다[37: '대하다2']. 국립국어원은 "‘지원 대상에 대한 수요 조사’라는 표현은 ‘지원 대상’을 수요 조사의 대상으로 삼는다는 의미를 나타내는 것으로 적절한 표현입니다"라고 답했습니다[27: 328851번]. 『한눈에 알아보는 공공언어 바로 쓰기』가 고쳐 쓴 모범 문장에도 "응급 의료에 대한 시민의 관심"이 있습니다[2: 11쪽].
  이근희가 과학 기사 번역에서 분류한 번역투 39종에 `-에 대한`은 없습니다. 이근희가 제시한 대안 문장 "ITER의 내벽 재료에 대한 결정을 내리기까지 약 2년이 남았다"에도 `-에 대한`이 그대로 있습니다[35: 278-279쪽]. 최정애는 동작성 명사의 논항에 `의`를 붙이거나 아무 표지도 붙이지 않으면 문법성이 떨어지거나 비문법적이 되고 `에 대한`이나 `에 의한`을 붙이면 문법성이 높아진다고 봅니다[40]. ## 격식 있는 문어체

답변을 포함한 모든 글을 업무 문서처럼 격식 있는 문어체로 쓰는 것은 이 repository가 정한 규칙입니다. 표준국어대사전은 `문어체`를 "일상적인 대화에서 쓰는 말투가 아닌, 글에서 주로 쓰는 말투."로 풀이합니다[37: '문어체']. 같은 사전은 `격식체`를 "상대 높임법의 하나. 의례적으로 쓰며 표현은 직접적, 단정적, 객관적이다. 해라체, 하게체, 하오체, 하십시오체 따위가 있다."로 풀이합니다[37: '격식체']. 이 repository가 쓰는 합니다체는 하십시오체이므로 이미 격식체입니다. 따라서 이 절은 종결 어미가 아니라 낱말과 표현을 다룹니다. 종결 어미는 '말투' 절에서 다룹니다.

**답변도 업무 문서처럼 문어체로 씁니다.** 국립국어원은 "보도 자료는 문어이므로 구어 표현을 쓰지 않는데, 예를 들어 문장 종결에 '-구요'를 쓰거나 '-기에' 대신 '-길래'를 쓰는 경우, '매우'의 뜻으로 '되게'를 쓰는 일이 없어야 한다."라고 합니다[43: 52쪽]. 같은 쪽에서 "보도 자료의 목적상 대체로 문어에 맞는 표현을 써야 공공언어로서의 품위를 지킬 수 있다."라고 합니다. 국립국어원은 "선정되었음을 알고 있으시죠?"를 "선정되었음을 알고 계실 것입니다."로 고치고 "격식을 갖춘 문서이므로 '하십시오체'를 사용한다."라고 설명합니다[2: 103쪽]. 국립국어원은 "공식적인 상황이거나 덜 친밀한 관계에서는 직장 사람들에게 직급에 관계없이" 하십시오체로 말하는 것이 바람직하다고 합니다[44: 159쪽]. 같은 쪽의 예문에는 "거래처에 전화하셨습니까?"처럼 일상 낱말이 쓰였습니다.
김남정과 권연진은 "고유어의 경우, 일상적이고 비공식적, 비격식적인 상황에 자주 사용되는 반면 한자어는 전문적이며 공식적, 격식적인 담화 상황에서의 사용이 두드러진다."라고 씁니다[45: 2쪽]. 이 문장은 저자들이 직접 측정한 결과가 아니라 김광해(1989)와 노대규(1996)를 인용한 기술입니다. 안의정은 새연세말뭉치의 문어와 구어 각 100만 어절에서 조사를 빼고 어종 비율을 계산했습니다[46: 294-295쪽]. 한자어는 문어에서 40.0%, 구어에서 20.9%였고 고유어는 문어에서 47.7%, 구어에서 70.8%였습니다.
이와 반대되는 자료도 있습니다. 법제처는 "어색한 문어체나 번역체 문장을 일상생활에서 사용하는 친숙하고 매끄러운 문체로 다듬는다."를 원칙으로 듭니다[47: 7쪽]. 같은 쪽에서 고어체에 가까운 문어적 표현이 법령의 위엄과 권위를 뒷받침한다고 생각하는 사람이 적지 않다고 지적합니다. Microsoft는 "Microsoft voice avoids an unnecessarily formal tone."이라고 하고[1: 6쪽] Google은 "aim for a conversational tone rather than a formal one"이라고 합니다[48]. 김자유는 소리 내어 읽었을 때 어색한 문장으로 "한자어를 쓰거나, 문어체를 쓰거나, 호흡이 지나치게 긴 문장들"을 듭니다[49]. 다만 김자유가 소개한 원칙은 토스가 제품 화면 문구를 쓸 때 따르는 원칙입니다. 국립국어원 온라인가나다는 "'구어체'나 '문어체'라는 것은 그 범위가 명확히 정해져 있는 것이 아니므로 어떠한 표현이 구어체인지 아닌지 단정하기는 어렵습니다."라고 답했습니다[27: 326949번]. 또 '우선'이 문어체인지 "판단할 근거가 사전이나 규범에 따로 명시되어 있지 않아" 단정하기 어렵다고 답했습니다[27: 337496번].
채팅 답변까지 문어체로 쓰라는 외부 자료는 찾지 못했고 조사한 회사 가이드 가운데 격식 있는 문어체를 권하는 것도 없었습니다. 그러므로 답변을 포함한 모든 글을 문어체로 쓰는 것은 이 repository의 규칙입니다. 법제처의 지적에 따라 `~하는 바입니다`, `~할지어다` 같은 예스러운 말투를 쓰지 않는 것도 이 repository의 규칙입니다.

**일상 한자어는 그대로 씁니다.** 국립국어원은 "한자어는 우리말에서 빼놓을 수 없는 중요한 자원이지만 필요 이상으로 어려운 한자어를 사용하는 경우에는 소통을 가로막는다."라고 하며 "순우리말이나 좀 더 쉬운 한자어"로 쓰라고 합니다[43: 93쪽]. 표준어 규정 제21항 해설은 "단순히 한자어라는 이유로 표준어에서 제외되는 것은 아니다."라고 하고 제22항 해설은 "고유어라고 하여도 쓰임이 없으면 표준어로 삼지 않은 것이다."라고 합니다[50]. 법제처는 "일본식 한자어라도 바꾸어 사용할 만한 우리말을 찾기 어렵거나 우리말이 법령문에서의 원래 의미를 나타내지 못하면 바꾸지 않는다."라고 합니다[47: 36쪽]. 행정안전부가 2016년에 만든 순화 목록은 `관할 → 담당`, `유관기관 → 관계기관`처럼 한자어를 더 쉬운 한자어로 바꿉니다[51: 19쪽].
정부 자료의 교정문에도 일상 한자어가 그대로 남아 있습니다. 국립국어원의 교정문에는 "일괄적으로 공사하는 것으로 변경하고"가 있습니다[2: 43쪽]. 국립국어원의 권장 표현에는 "내외부 사정으로 변경될"이 있습니다[9: 13쪽]. 국립국어원은 원문의 "동일하게"를 고칠 대상으로 표시하지 않았습니다[2: 46쪽]. 법제처는 `균분하다`의 대안으로 "동일하게 나누다"를 듭니다[47: 20쪽]. 국립국어원은 "10월초 현재까지"의 띄어쓰기만 고칩니다[2: 22-23쪽]. 국립국어원의 교정문에는 "해당 전자 우편"이 있습니다[2: 51쪽]. 국립국어원과 법제처는 `당해`를 `해당`으로 바꿉니다[2: 147쪽][47: 73쪽]. 국립국어원은 "당초"를 "기존"으로 고칩니다[2: 25쪽]. 같은 쪽의 교정문에는 "갱신을 매달 진행해 주십시오"도 있습니다. 국립국어원의 교정문에는 "감면 대상임이 확인되면"도 있습니다[2: 59쪽].
회사 가이드도 `변경`을 씁니다. Microsoft의 고친 문장은 "암호를 변경하려면 다음 단계를 따르세요"입니다[1: 7쪽]. 토스 가이드의 '구체적으로 쓰기' 페이지에 실린 좋은 예문에는 "설정 파일을 변경하면 기존 설정이 삭제됩니다."가 있습니다[10]. 카카오디벨로퍼스의 예문에는 "다른 문구로 변경할 수 없습니다"가 있습니다[52]. 국립국어원은 명사를 쌓은 문장도 고칩니다. "다양한 지식과 정보 제공을 위하여"를 "다양한 지식과 정보를 제공하고자"로 고치는데, 한자어 `제공`은 두고 명사구만 동사로 바꾼 것입니다[2: 35쪽]. 또 "도시계획 도로 공사를 진행 중에 있습니다"를 "도시계획 도로 공사를 진행하고 있습니다"로 고칩니다[2: 43쪽].
이와 반대되는 자료도 있습니다. 국립국어원의 다듬은 말에는 "동일한 → 같은"이 남아 있으며 출처는 문교부 『국어순화자료』 제5집(1982), 『국어순화자료-학교 교육용』(1983), 『국어순화자료집』(1992)입니다[53: '동일한']. 같은 목록에는 1983년과 1992년 자료에서 가져온 "제공하다 → 바치다, 내다"도 남아 있습니다[53: '제공하다']. 토스 가이드의 '자연스러운 한국어 표현 쓰기' 페이지에 실린 실습에서는 "설정 변경을 수행한 후 적용을 진행합니다."를 "설정을 바꾼 뒤 적용합니다."로 고친 문장이 정답입니다[10].
그러나 일상 한자어를 고유어나 구어로 바꾸지 않는 것은 이 repository의 규칙입니다. 이 규칙이 다루는 낱말은 변경, 동일, 현재, 해당, 기존, 확인, 제공, 진행, 완료, 유지, 적용, 재시작, 이후, 이전입니다. 다듬은 말 목록의 오래된 항목보다 최근 교정문을 따르기로 한 것도 이 repository의 판단입니다. 낱말은 고유어인지 한자어인지가 아니라 실제 쓰임으로 고르며 그 근거는 표준어 규정 해설입니다[50]. `지금`도 표준국어대사전에 원어 `只今`으로 오른 한자어입니다[37: '지금2']. 일상 한자어를 쓰더라도 명사를 쌓아 동작을 숨기지 않습니다. 자세한 규칙은 '문장' 절의 '명사를 쌓지 말고 동사로 씁니다' 문단에 있습니다.

**한자 관형사와 어려운 한자어는 쓰지 않습니다.** 국립국어원은 '어려운 한자어를 남용하지 않는다' 항목에서 `제고`, `제반`, `소정의`, `타`, `동`이 든 표현을 쉬운 말로 고칩니다[9: 13쪽]. 고친 예는 아래 표에 있습니다. 국립국어원은 "동 건은"을 "이 건은"으로 고치고 "'동'이라는 한자어 대신에 순우리말 '이'를 쓰면 더 이해하기 쉽다."라고 설명합니다[2: 31쪽]. 또 "상이한"을 "(서로) 다른"으로 고칩니다[2: 43쪽].

법제처는 법령 정비 예에서 "동법 제5조의2의 규정에 의한"을 "같은 법 제6조에 따른"으로 고칩니다[47: 33쪽]. "'당해'는 법령문 외에는 잘 쓰지 않는 한자어이다."라고 하며 `해당`이나 `그`로 바꿉니다[47: 73쪽]. 행정안전부의 2016년 순화 목록은 "타 학교"를 "다른 학교"로, "제고하고"를 "높이고"로, "금번"을 "이번"으로, "익일"을 "다음 날"로 바꿉니다. 같은 목록은 "향후"를 "앞으로"로, "의거"를 "따름"으로, "상이한"을 "서로 다른"으로, "당해"를 "그"로 바꿉니다[51: 19쪽]. 국립국어원의 다듬은 말 이력을 보면 "본건 → 이 사건, 이 일"은 1978년부터 순화 자료에 올랐고 2012년 4월 16일 제2차 국어심의회 국어순화분과 회의에서 다시 확정됐습니다[53: '본건']. "동법 → 같은 법"은 문화체육관광부고시 제2013-9호(2013. 3. 8.)에 근거하며[53: '동법'] "제고하다 → 높이다"는 1977년 자료부터 올라 있습니다[53: '제고하다']. 국립국어원 온라인가나다는 "'본'이 일본식 표현이라고 직접적으로 기술된 내용은 찾을 수 없고"라고 하면서 다듬은 말 목록을 근거로 "'이 프로그램'으로 표현하실 수 있음을 참고하시기 바랍니다."라고 답했습니다[27: 307021번]. 카카오엔터프라이즈 테크니컬라이팅팀은 예시 문장의 "본 가이드"를 불필요한 표현으로 표시하고 "단도직입적으로 설명하면"은 한자어와 비유 표현으로 표시합니다[54].
이해도에 관한 근거도 있습니다. 홍준표는 성인 1,100명에게 공공언어를 이해하기 어려운 이유를 최대 2개까지 고르게 했고 "낯선 한자어 등 어려운 단어"를 고른 비율이 63.0%였다고 합니다[55: 65쪽]. 신명선 외는 보도 자료에 나온 2음절 한자어의 뜻을 물었습니다. 12점 만점에서 고등학생 평균은 3.70점, 대학생 평균은 7.57점이었다고 합니다[56: 162쪽].
이 낱말들은 규범상 오류가 아닙니다. 국립국어원 온라인가나다는 `제고하다`가 든 문장이 "사용하기에 문제가 없는 것으로 보입니다"라고 답했고[27: 334106번] `서로 상이하다`를 틀렸다고 보기 어렵다고 답했습니다[27: 331421번].
따라서 이 낱말들을 쓰지 않는 것은 규범이 아니라 문체에 관한 이 repository의 규칙입니다. 이 repository는 `본 PR`을 `이 PR`로, `타 모듈`을 `다른 module`로, `동 함수`를 `같은 함수`로 씁니다. `제고`, `향후`, `익일`, `금번`, `상이`, `당해`, `제반`, `소정의`, `의거`는 각각 `높이다`, `앞으로`, `다음 날`, `이번`, `다르다`, `해당`, `모든`, `정해진`, `따라`로 씁니다. 검사기는 `당해`를 뺀 여덟 낱말과 `당해 연도`, 관형사 `본`, `타`, `동`을 `hanja-word` 경고로 알립니다. 문어체를 지시하면 이런 말이 늘어날 위험이 있다고 이 repository는 판단합니다. 근거는 Lee의 논문입니다[6: 22쪽]. 이 논문은 한국어 학술 초록에서 한자어 학술 동사 12개의 초록당 빈도가 2022년 0.40에서 2026년 1.11로 늘었다고 보고합니다. 고유어 표현 10개의 초록당 빈도는 2022년까지 1.07과 1.12 사이였다가 2026년에 0.80으로 줄었습니다. 저자는 이 변화가 LLM 사용과 관련이 있다고 봅니다. 다만 이 논문은 동료 심사를 거치지 않았습니다.

**구어 표현은 쓰지 않습니다.** 국립국어원이 보도 자료에서 구어 표현을 빼라고 한 원문은 앞의 '답변도 업무 문서처럼 문어체로 씁니다' 문단에 있습니다[43: 52쪽]. 같은 쪽에서 국립국어원은 교정 예 세 가지를 듭니다. "우리를 도와줬고"는 "우리에게 도움을 주었고"로 고칩니다. "하지만 권익위 실태조사 결과"는 "그러나 권익위 실태 조사 결과"로 고칩니다. "아리송해하는 경우가 많았다"는 "알지 못하는 경우가 많았다"로 고칩니다. 국립국어원은 이어서 "'도와주다, 하지만, 아리송해하다'처럼 구어적이거나 주관적 감정이 개입된 듯한 어휘는 피하는 것이 좋다."라고 보충합니다. 한편 표준국어대사전은 `하지만`을 "서로 일치하지 아니하거나 상반되는 사실을 나타내는 두 문장을 이어 줄 때 쓰는 접속 부사."로 풀이하고 구어 표시를 두지 않습니다[37: '하지만'].
이 repository는 `-구요`, `-길래`, `되게`, `좀`, `근데`, 접속 부사 `그러니까`를 쓰지 않습니다. 이 가운데 `-구요`, `-길래`, `되게`는 국립국어원 자료에 나오고 `좀`, `근데`, `그러니까`는 이 repository가 추가했습니다. `하지만`보다 `그러나`를 권하는 것도 이 repository의 규칙입니다. 근거가 교정 예 하나뿐이고 사전에 구어 표시가 없으므로 금지가 아니라 권고입니다. 검사기는 `-구요`, `-길래`, `되게`, `근데`를 `colloquial` 경고로 알립니다. 접속 부사를 고르는 기준은 '접속 부사' 절에 있습니다.

**`이외`와 `외`는 앞에 꾸미는 체언이 있을 때 씁니다.** 표준국어대사전은 `이외`를 "일정한 범위나 한도의 밖."으로 풀이합니다[37: '이외1']. 국립국어원 온라인가나다는 명사 `이외`를 "'먹을 것 이외/관계자 이외'처럼 앞에서 체언 등의 수식을 받는 경우에 사용"한다고 답했습니다[27: 324074번]. 또 사전 용례 "이곳은 관계자 이외의 사람이 들어올 수 없습니다."를 소개하고 `의`를 빼고 "예약자 이외 동반인 입장이 불가합니다."로 써도 틀린 것은 아니라고 답했습니다[27: 334643번]. 이 예문에는 앞에 체언 `예약자`가 있습니다. 국립국어원 온라인가나다는 '외'를 쓴 표현이 "일정한 범위나 한도의 밖"을 나타낼 뿐 항상 "앞의 것을 제외하고"라는 뜻으로 쓰이지는 않는다고 답했습니다[27: 330699번]. 대신 쓸 표현으로는 "'…를 제외하고', '…를 포함하고' 등의 표현"을 들었습니다. 법제처는 `기타`를 관형어 `그 밖의`나 부사어 `그 밖에`로 바꾸며 "'그 밖의'를 쓸지 '그 밖에'를 쓸지는 문장에서 수식관계를 고려하여 선택한다."라고 합니다[47: 75쪽].
앞에 꾸미는 체언이 없으면 `그 밖의`를 쓴다는 것은 이 repository의 규칙입니다.

**고유어를 한자어로 바꿀 때는 뜻과 앞뒤 말에 어울리는지 확인합니다.** 김남정과 권연진은 "상황 맥락에 맞지 않는 발화는 정확성의 문제보다는 적절성과 관련이 있다."라고 합니다[45: 2쪽]. 윤주리와 송정근은 "'현재'는 구어적 표현과 자연스럽게 공기하지 못하고"라고 하며 예문으로 "주환아, 지금/이제/?현재 학교에 가니?"를 듭니다[57: 372쪽]. 또 "'지금'보다는 '현재'가 더 광범위한 시간대를 지시한다."라고 합니다[57: 374쪽]. 최지희는 초록에서 "'사다'는 구어에서, '구입하다'는 문어에서 주로 출현하여 사용역에서 차이를 보였다."라고 하고 `구매하다`는 사는 행위 자체에 초점이 있어 `사다`, `구입하다`와 뜻이 다르다고 봅니다[58]. 손연정은 초록에서 고유어와 한자어 유사 표현이 "연어, 제약, 담화 기능 등의 영역을 보면 서로 다른 양상으로 사용된다"고 합니다[59]. 고유어를 한자어로 바꾸면 더 정확해진다는 연구는 찾지 못했고 같은 내용을 한자어 문장과 고유어 문장으로 써서 이해도를 비교한 실험도 찾지 못했습니다.

## 말투

표준국어대사전은 하십시오체를 상대편을 아주 높이는 종결형으로 풀이합니다[37: '하십시오체']. 해요체는 격식체인 하오체와 하십시오체를 쓸 자리에 두루 쓰는 비격식체로 풀이합니다[37: '해요체']. `합니다체`와 `다나까체`는 표준국어대사전에 없습니다[37]. 우리말샘은 `다나까체`를 `-다`나 `-까`로만 끝나는 말의 종결형으로 풀이하고 주로 군대에서 쓰는 언어 예절을 가리키는 말이라고 덧붙입니다[60: '다나까체'].
표준국어대사전은 `-습니다`와 `-ㅂ니다`를 하십시오할 자리에 쓰는 어미로 풀이합니다[37: '-습니다']. 그러므로 이 repository가 `합니다체`라고 부르는 말투는 사전 용어로 하십시오체입니다. 하십시오체라는 이름만으로는 `~합니다`로 끝나는 서술이 바로 떠오르지 않아 `합니다체`라는 이름을 씁니다. 0.3.0까지 쓰던 `다나까체`는 군대 말투를 떠올리게 해서 바꿨습니다. 해요체와 하십시오체는 표준국어대사전 표제어이므로 따옴표 없이 붙여 씁니다.

어떤 말투를 쓸지는 자료마다 다릅니다. Microsoft와 Mozilla는 `~합니다` 서술과 `~하세요` 요청을 함께 씁니다[1][61]. 카카오디벨로퍼스는 서술하는 문장을 `-니다`로 끝냅니다. 행동을 유도하는 문장도 `~하십시오`나 `~하세요` 대신 `~합니다`나 `~해야 합니다`로 씁니다[52]. 카카오엔터프라이즈 테크니컬라이팅팀은 기술 문서에서 `~다`로 끝나는 서술식 문장을 쓰는 것이 일반적이라고 합니다[23]. 토스는 제품 문구를 해요체로 통일합니다[62]. 토스 테크니컬 라이팅 가이드는 해요체와 하십시오체를 섞어 씁니다[10]. 쿠버네티스 한국어 문서는 `~한다`로 끝내는 평어체가 원칙입니다[33].
국립국어원은 하십시오체와 해요체를 섞어 쓰는 문제를 어문 규정에서 따로 다루지 않는다고 답했습니다. 다만 글은 보통 한 문체로 쓴다는 점을 참고하라고 덧붙였습니다[27: 318384번].
이 repository는 합니다체를 기본으로 하고 요청은 `~해 주십시오`로 씁니다. 해요체를 고른 프로젝트에서는 `~해요`와 `~해 주세요`를 씁니다.

**명령을 메모처럼 줄이지 않습니다.** 국립국어원은 `다음과 같이 작성할 것.`을 `다음과 같이 작성해 주십시오.`로, `7일 내로 즉시 제출 바람.`을 `7일 내로 제출해 주십시오.`로 고칩니다. `-ㄹ 것`은 명령이나 시킴의 뜻으로 문장을 끝맺는 말이므로 피하고 `즉시 ~ 바람`처럼 고압적인 느낌을 주는 표현 대신 `주십시오`처럼 공손하게 쓰라고 합니다[12: 12쪽].

**`-시-`는 사람이 주어일 때만 붙입니다.** 국립국어원은 사물이 주어인 `이 제품은 품절이십니다`를 `품절입니다`로 고칩니다[63].

## IT 용어 표기

이 repository는 개발자가 읽는 글에서 IT와 공학 용어를 영어 원어로 쓰고 일반 어휘는 한국어로 씁니다. 이 규칙은 업계 대다수가 따르는 관행이 아니라 이 repository가 정한 기본값입니다. 국내 회사의 기술 블로그, 해외 회사의 한국어 문서, 국립국어원 자료는 대부분 IT 용어를 한글로 적습니다. 이 사실을 보여 주는 자료는 아래 '반대 근거' 절에 모았습니다.

### 이 repository의 규칙

**개발자가 읽는 글에서는 IT와 공학 용어를 영어 원어로 씁니다.** 개발자가 읽는 글은 답변, 개발 문서, README, commit 메시지, PR, issue, 코드 주석, 검사기와 hook이 출력하는 메시지입니다. 음차(`커밋`, `머지`, `리포지토리`)와 번역어(`저장소`, `병합`, `배포`)는 모두 쓰지 않습니다. 예를 들어 `커밋을 푸시한 뒤 배포했습니다`는 `commit을 push한 뒤 deploy했습니다`로 고칩니다. 검사기는 개발자가 읽는 파일에 쓴 음차를 `transliteration` 오류로 막습니다. 일반 뜻으로도 흔히 쓰는 음차와 번역어는 경고로만 알립니다.

**일반 어휘와 완전히 정착한 일반어는 한글로 씁니다.** 일반 어휘에는 확인, 검증, 검사, 요청, 응답, 설정, 알림, 조건, 설치, 실행, 출력, 입력, 명령, 경로, 환경 변수, 규칙, 문서, 답변, 질문이 듭니다. 이 repository가 정한 정착한 일반어는 파일, 프로젝트, 버전, 클라우드, 메시지, 프로그램, 컴퓨터, 인터넷, 이메일, 앱, 웹, 메뉴, 버튼, 화면입니다.

**제품 이름, 고유명사, 약어, 코드, 명령, 경로, 설정 키, 환경 변수는 원문 그대로 둡니다.** `GitHub`, `Claude Code`, `Node.js`, `PR`, `API`, `CI`, `npm run gate`가 그런 예입니다. 그 밖의 영어 용어는 소문자 원형으로 씁니다. 쿠버네티스 한글화 팀도 필드 이름과 파일 이름, 경로를 원문 그대로 둡니다[33]. 카카오디벨로퍼스는 플랫폼과 프로그래밍 언어 이름을 영문 그대로 씁니다[52].

**문장, 제목, 목록 항목, 표 칸이 영어 낱말로 시작하면 첫 글자를 대문자로 씁니다.** 2026년 11월 7일 사용자는 README의 `bug와 제안은 Issues에 남겨 주십시오. pull request를 환영합니다.`를 보고 문장 첫 글자를 대문자로 써야 한다고 지적했습니다. 그때까지 skill은 제품 이름, 고유명사, 약어가 아닌 영어 용어를 소문자 원형으로 쓰라고만 했고 문장 첫머리는 따로 다루지 않았습니다. 그래서 Claude는 문장 첫머리에서도 `commit`, `pull request`를 소문자로 썼습니다. 검사기에도 이런 표기를 잡는 규칙이 없었습니다. 영어 문장의 첫 글자를 대문자로 쓰는 관례를 한국어 문장 첫머리의 영어 낱말에도 적용하는 것은 이 repository의 규칙입니다. 코드, 명령, 경로, 파일 이름과 `npm`, `macOS`처럼 공식 표기가 소문자로 시작하는 이름은 그대로 둡니다. 검사기가 잡지 않을 이름은 규칙 문서의 `lowercase-start-exempt`에 적습니다. 검사기는 파일, commit 메시지, PR과 issue에 올리는 글에서 첫머리를 소문자로 쓴 영어 낱말을 `lowercase-start` 오류로 막고 답변에서는 경고로만 알립니다.

**사용자가 준 글은 표기를 바꾸지 않습니다.** 사용자가 준 글을 옮기거나 다듬을 때는 그 글의 용어 표기를 그대로 둡니다. 이 절의 규칙은 Claude가 새로 쓰는 문장에만 적용합니다. 팀이 규칙 문서의 용어표를 고치면 검사기가 잡는 표기만 바뀝니다. Claude가 IT 용어를 한글로 적게 하려면 프로젝트의 `CLAUDE.md`에 그렇게 적어야 합니다.

### 영어로 쓸 말을 고르는 기준

**어느 말을 영어로 쓸지는 skill의 '용어 표기' 절과 규칙 문서의 용어표가 정합니다.** 두 곳에 없는 IT 용어는 다음 순서로 판단합니다.

1. 제품 이름, 고유명사, 약어, 코드, 명령, 경로, 설정 키, 환경 변수이면 원문 그대로 둡니다. Kubernetes의 `Deployment`처럼 제품이 정한 resource 이름은 원문의 대소문자를 유지합니다.
2. 고유어나 한자어이면 한국어로 둡니다. 다만 `저장소`, `병합`, `배포`, `분기`, `의존성`처럼 개발 개념을 가리키려고 영어를 옮긴 번역어는 영어로 바꿉니다. `요청`, `응답`, `경로`, `명령`처럼 개발과 관계없는 글에서도 같은 뜻으로 쓰는 말은 일반 어휘로 봅니다.
3. 외래어이면 정착한 일반어 목록에 있는지 확인합니다. 목록에 있으면 한글로 쓰고 없으면 영어 원어로 씁니다.

**정착한 일반어 목록은 이 repository가 낱말마다 정한 목록입니다.** 표준국어대사전에 올랐는지나 일상 글에서 얼마나 쓰이는지 하나만으로 정하지 않습니다. `서버`, `폴더`, `브라우저`는 표준국어대사전에 정보 통신 분야의 뜻으로 올라 있습니다. `데이터`는 셋째 뜻이 정보 통신 분야의 뜻이고 `테스트`는 일반 뜻으로 올라 있습니다[37]. 그러나 이 repository는 이 다섯 낱말을 IT 용어로 보고 `server`, `folder`, `browser`, `data`, `test`로 씁니다. 반대로 `클라우드`는 표준국어대사전에 표제어가 없지만 이 repository는 정착한 일반어로 보고 한글로 씁니다. 목록을 바꾸려면 skill의 '용어 표기' 절, 규칙 문서의 용어표, 이 절을 함께 고칩니다.

**글자만 같은 말은 고치지 않습니다.** 용어표의 한글 표기가 들어 있어도 다른 낱말이거나 다른 뜻으로 쓴 말은 그대로 둡니다. `나머지`, `머지않아`, `캐시백`, `1분기`, `보도자료를 배포했습니다`가 그런 예입니다.

### 조사와 용언

**영어 용어 뒤의 조사는 그 용어를 한글로 읽은 소리에 맞춰 고르고 띄어 쓰지 않습니다.** 읽는 소리는 외래어 표기법에 따른 한글 표기를 기준으로 합니다. 따라서 철자가 비슷해도 한글 표기가 다르면 조사가 달라집니다. `stack`은 `스택`으로 적으므로 `stack이`라고 쓰고 `task`는 `태스크`로 적으므로 `task가`라고 씁니다.

| 한글로 읽은 소리의 끝 | 조사 | 예 |
| --- | --- | --- |
| 받침이 없음 | 를, 가, 는, 와, 로 | `cache를`(`캐시`), `test를`(`테스트`), `server가`(`서버`), `data는`(`데이터`) |
| ㄹ이 아닌 받침이 있음 | 을, 이, 은, 과, 으로 | `commit을`(`커밋`), `hook으로`(`훅`), `Git이`(`깃`) |
| ㄹ 받침이 있음 | 을, 이, 은, 과, 로 | `model로`(`모델`), `PR을`(`피알`), `PR로`(`피알`) |

국립국어원은 영어 뒤에 붙는 조사를 묻는 질문에 "규정으로 명확히 정해진 바는 없으나, 우리말 표현에 준한다면 우리말 표기인 '브레드'에 맞추어 'bread를'처럼 씀이 적절해 보입니다."라고 답했습니다[27: 311010번]. GitLab의 한국어 기술 문서 번역 지침도 조사를 발음에 맞추게 하고("Apply to English words based on pronunciation.") 영어 낱말과 조사 사이를 띄우지 않게 합니다("No space between a particle and an English word.")[73]. 한글 뒤 괄호에 영어를 덧붙였으면 괄호 앞의 말에 조사를 맞춥니다. 국립국어원은 이를 관례로 보고 "'빵(bread)을'처럼 씀이 적절합니다"라고 답했습니다[27: 311010번].

**바뀌는 값 뒤에는 범주 명사를 붙입니다.** `${name}`처럼 바뀌는 값은 읽는 소리를 정할 수 없으므로 `${name}을`을 `${name} 파일을`처럼 고칩니다. Microsoft는 이 자리에 `을(를)`처럼 두 조사를 함께 적고[1] GitLab은 `은(는)`을 씁니다[73]. 이 repository는 `%s 부가기능은`처럼 범주 명사를 붙이는 Mozilla의 방식을 따릅니다[61].

**`-하다`, `-되다`는 영어 용어에 붙여 씁니다.** `deploy합니다`, `build됩니다`, `push했습니다`, `merge할`처럼 씁니다. 국립국어원은 외래어에 붙는 `-하다`를 두고 "사전에 없더라도 접미사 '-하다'를 결합하여 쓸 수 있는 경우에는 붙여 씁니다."라고 답했습니다[27: 333949번]. 행위나 상태를 나타내는 외래어 명사를 두고는 "해당 표현이 사전에 등재되어 있지 않더라도 이들 접미사를 결합하여 쓸 수 있습니다."라고 답했습니다[27: 335401번]. 영어와 한글을 함께 적을 때의 띄어쓰기를 묻는 질문에는 "규정으로 정해진 바 없으나, 접미사를 띄어 쓸 근거는 없어 보입니다."라고 답했습니다[27: 322259번]. 이 답변들은 한글로 적은 외래어나 `-지`, `-씨` 같은 접미사를 다룬 것입니다. 영문자 뒤의 `-하다`, `-되다`를 붙여 쓰는 규칙은 이 repository가 이 답변들을 넓혀 적용한 것입니다.
국내 기술 블로그 194편에서도 영어 낱말 뒤에 `-하다`, `-되다`를 붙여 쓴 곳이 90곳이고 띄어 쓴 곳은 8곳이었습니다[72]. 토스는 "DAG를 실제로 import해 보고"[74], "기존 LLM으로 Fallback합니다"[75]처럼 붙여 씁니다. Pro Git 한국어판은 "리모트 저장소를 관리하면서 데이터를 거기에 Push 하고 Pull 하는 것이다."처럼 대문자로 시작하는 영어 뒤를 띄어 씁니다[70]. 이 repository는 이런 표기를 `push하고 pull하는`처럼 고칩니다.

**한국어 접두사를 영어 용어에 붙이지 않습니다.** `재deploy`는 `다시 deploy`로 고칩니다. `재설치`, `재시작`처럼 한자어로 된 일반 어휘는 그대로 씁니다. GitLab 지침은 한자어 `호출`에 붙은 `재`도 `다시`로 바꿔 `API를 재호출합니다` 대신 `API를 다시 호출합니다`를 쓰게 합니다[73].

### 일반 독자가 읽는 글

**일반 독자가 읽는 글에는 영어 원어 규칙을 적용하지 않습니다.** 이 예외에 드는 글은 웹 페이지, 이용자 공지, 앱 문구, 개인정보 처리방침, 약관, 앱 스토어 설명, 이용자에게 보내는 업데이트 소식, 고객 도움말입니다. 이런 글에서는 개발 용어를 독자가 화면에서 보는 말로 풀고 사전에 오른 외래어를 한글로 적습니다. 예를 들어 `오늘 새벽 v2.3을 deploy했습니다`는 `오늘 새벽 2.3 버전으로 업데이트했습니다`로 고칩니다. 표준국어대사전은 `페이지`, `브라우저`, `쿠키`, `클릭`, `스크롤`을 정보 통신 분야의 뜻으로 올려 두었습니다[37]. 개인정보보호위원회 작성지침의 작성 예시도 `쿠키`와 `브라우저`를 한글로 씁니다[19]. 따라서 이런 글에서는 `page`, `browser`, `cookie`, `click` 대신 한글 표기를 씁니다.
앞의 개인정보 처리방침 예문이 나온 프로젝트는 개발 문서에 `page`, `file`, `deploy`를 영어로 적습니다. Claude는 방문자가 읽는 처리방침에서도 `page`, `browser`, `cookie`를 영어로 적었습니다. 그래서 skill에는 "프로젝트 문서가 이런 말을 영어로 적어도 일반 독자가 읽는 글은 독자의 말을 따릅니다."라는 지시가 들어 있습니다. 검사기는 일반 독자가 읽는 글로 지정한 파일에 IT 용어 표 규칙을 적용하지 않습니다.

**예외 여부는 글의 주제가 아니라 독자로 정합니다.** 개발자에게 보내는 release note는 개발자가 읽는 글입니다. 같은 변경을 이용자에게 알리는 업데이트 소식은 일반 독자가 읽는 글입니다. 이 구분은 이 repository가 정한 것입니다.

이 예외의 근거는 다음과 같습니다. 국어기본법 제14조 제1항은 "공공기관등은 공문서를 일반 국민이 알기 쉬운 용어와 문장으로 써야 하며, 어문규범에 맞추어 한글로 작성하여야 한다. 다만, 대통령령으로 정하는 경우에는 괄호 안에 한자 또는 다른 외국 글자를 쓸 수 있다."라고 정합니다[76]. 이 조항은 공공기관의 공문서에 적용됩니다. 국립국어원의 공공언어 지침은 `LED`를 예로 들어 "외국 문자를 써서는 안 되고, 「외국어 표기법」에 따라 한글로 적거나 다듬은 우리말로 적는다. 꼭 필요하다면 괄호 안에 외국 문자를 쓸 수 있다."라고 설명합니다[2: 61쪽]. 인용문의 「외국어 표기법」은 원문 그대로입니다. Microsoft의 한국어 현지화 지침은 "use technical terms for technical audiences, but for consumers use common words and phrases instead."라고 합니다[1: 5쪽]. 국립국어원은 문서를 읽는 사람의 관점에서 용어를 쓰는 것이 좋다고도 합니다[2: 45쪽].

**국내외 번역 지침.** 쿠버네티스 문서 한글화 가이드는 "영문 용어를 한글화할 때는 다음의 우선 순위를 따르나, 자연스럽지 않은 용어를 무리하게 선택하지는 않는다."라고 하고 한글 단어, 한영 병기, 영어 단어 순으로 우선순위를 둡니다. 이 가이드의 용어집은 build를 `빌드`, cache를 `캐시`, repository를 `리포지터리`, shell을 `셸`로 정했습니다[33]. 카카오디벨로퍼스 문서 스타일 가이드는 "범용적으로 쓰이는 용어에 한해 외래어 표기법(참고: 국립국어원 한국어 어문 규범)에 맞춰 국문으로 작성합니다."라고 합니다. 영어는 "플랫폼, 프로그래밍 언어, 국문으로 표현이 어색한 영문 용어"에만 그대로 씁니다[52]. 토스의 테크니컬 라이팅 가이드는 "토스에서는 구글 트렌드 기준으로 외래어 표기법보다 5배 이상 많이 사용되는 표기가 있으면 그 표기를 사용해요."라고 하며 `프론트엔드`를 예로 듭니다[10]. **국립국어원 자료와 법령.** 외래어 표기법 제1항은 "외래어는 국어의 현용 24 자모만으로 적는다."라고 정합니다[68]. 한글 맞춤법 제3항 해설은 외래어를 "고유어, 한자어와 함께 국어의 어휘 체계에 정착한 어휘"로 설명합니다. 또 "현실적으로는 국어사전에 실린 어휘는 외래어, 실리지 않은 것은 외국어로 구별하는 것이 편리하다."라고 합니다[82]. 이 기준에 따르면 표준국어대사전에 오른 `서버`, `데이터`, `테스트`, `폴더`, `브라우저`는 외국어가 아니라 국어 어휘입니다. 국립국어원은 외국 프로그램의 메뉴를 번역하는 질문자에게 "책 집필이나 번역에서 외래어를 반드시 피해야 한다고 보기는 어렵습니다. 쉬운 우리말이나 한자어로 자연스럽게 바꿀 수 있으면 그 표현을 쓰는 것도 좋겠습니다."라고 답했습니다[27: 335214번]. 국립국어원은 개발 용어도 우리말로 다듬어 왔습니다. `머지`는 `합치기`, `푸시`는 `밀기`, `디버깅`은 `벌레잡기`, `로그인`은 `회원 들어가기`, `웹 브라우저`는 `웹 탐색기`, `오픈 소스`는 `공개 소스`로 다듬었습니다[53]. 국어기본법 제14조는 공공기관의 공문서를 한글로 쓰게 하고 국립국어원의 공공언어 지침은 외국 문자를 쓰지 말라고 합니다[76][2: 61쪽]. 두 자료는 공공기관의 글에 적용되지만 IT 용어를 영문자로 적는 방식과는 방향이 반대입니다.

**연구.** 심재기는 한국정보통신기술협회의 정보 통신 용어 표준화가 "모든 심의 대상 용어는 모두 우리말로 표준화하는 것을 원칙으로 한다."라는 원칙을 따랐다고 소개합니다. 다만 "일반인에게도 이미 익숙하게 되었고, 그 개념도 널리 알려진 것은 원어 그대로 쓰는 것을 허용하였다."라고 하며 `하드웨어`, `소프트웨어`, `포털 사이트`를 예로 듭니다. 여기에서 '원어 그대로'는 한글로 적은 외래어를 가리킵니다[83]. 이현주는 "용어의 유입속도가 빠른 영역일수록 외국어, 특히 영어를 직접적으로 차용(borrowing)하는 빈도가 높으며"라고 지적합니다. 동시에 UNESCO의 2005년 지침을 인용해 "화자들이 전문지식을 모국어로 표현하지 못할 경우 정보와 지식을 얻는 과정에 불평등함이 야기될 수 있다."라고 경고합니다[84]. 최문선은 IT 발표 말뭉치를 분석해 IT 뜻의 deploy가 "일반적으로 한국어로는 ‘배포하다’라고 번역된다."라고 보고하고 build는 `빌드하다`, `빌드`로 음차한다고 정리합니다[85].

## 접속 부사

**접속 부사는 앞뒤 문장의 관계를 보고 고릅니다.** 사용자는 Claude가 쓴 다음 문단을 보여 주었습니다.

`Haiku 4.5 ID로 보낸 요청도 Sonnet 5로 호출합니다. 서울에는 Haiku 모델이 없기 때문입니다. 그래서 서비스는 모델 ID를 바꾸지 않아도 됩니다.`

사용자는 셋째 문장의 결론이 첫째 문장에서 나오는데도 `그래서`가 바로 앞의 이유 문장을 원인으로 받는 것처럼 읽힌다고 지적했습니다. 그리고 이 자리에는 `따라서`가 맞을 수 있으므로 문맥을 읽고 판단해야 한다고 했습니다. 이 repository는 둘째 문장을 셋째 문장의 근거로 읽으면 "서울에 Haiku model이 없으니 model ID를 바꾸지 않아도 된다"는 뜻이 되어 앞뒤가 맞지 않는다고 판단합니다.

**사전 풀이와 국립국어원 답변으로는 `그래서`와 `따라서`를 가를 수 없습니다.** 표준국어대사전은 `그래서`를 "앞의 내용이 뒤의 내용의 원인이나 근거, 조건 따위가 될 때 쓰는 접속 부사."로 풀이합니다. `따라서`는 "앞에서 말한 일이 뒤에서 말할 일의 원인, 이유, 근거가 됨을 나타내는 접속 부사."로 풀이합니다. `그러므로`는 "앞의 내용이 뒤의 내용의 이유나 원인, 근거가 될 때 쓰는 접속 부사."로 풀이합니다. 세 낱말은 서로를 「비슷한말」로 듭니다[37]. `그래서`의 풀이에도 '근거'가 있고 `따라서`의 풀이에도 '원인'이 있습니다. 따라서 사전 풀이만으로는 두 낱말을 가를 수 없습니다.
한국어기초사전도 `그래서`와 `따라서`를 똑같이 "앞의 내용이 뒤의 내용의 원인이나 근거, 조건 등이 될 때 쓰는 말."로 풀이하고 서로를 유의어로 듭니다[88]. 그러나 용례는 다릅니다. `따라서`의 용례는 "기업들이 환경을 파괴하는 데에는 경제적인 이유가 있다. 따라서 기업이 환경을 파괴하지 않고 이익을 낼 수 있는 제도의 마련이 필요하다."처럼 주장을 이끕니다. `그래서`의 용례는 "학교 가는 길에 차가 많이 막혔다. 그래서 지수는 제시간에 도착할 수가 없었다."처럼 일어난 일의 결과를 잇습니다[88].
국립국어원 온라인가나다는 `따라서`와 `그러므로`의 차이를 묻는 질문에 "두 단어 모두 앞의 내용이 원인, 이유, 근거일 때 쓰이며 격식성에서도 차이가 없어 보입니다. 그러므로 '따라서'와 '그러므로'는 거의 뜻이 동일한 유의어 관계에 있다고 볼 수 있습니다."라고 답했습니다[27: 327990번]. `그래서`와 `그러므로`의 차이를 묻는 질문에는 두 낱말의 사전 풀이와 용례만 제시했습니다. 그리고 "접속 부사의 구체적인 쓰임 차이를 일일이 말씀드리기는 어려우므로, 구체적인 쓰임은 사전 용례에서 확인하여 보시기를 권하여 드립니다."라고 답했습니다[27: 307744번]. 따라서 이 repository는 사전 규범으로는 `그래서`를 틀렸다고 할 수 없으며 `그래서`와 `따라서` 가운데 무엇을 쓸지는 앞뒤 문장의 관계를 보고 정할 문제라고 봅니다.

**연구는 `그래서`와 `따라서`가 쓰이는 관계가 다르다고 보고합니다.** 박건숙은 한국어능력시험 읽기 지문을 분석하여 "{그래서}는 [원인]과 [결과]의 접속에서 주로 사용되고 {따라서}는 [이유]와 [결론]의 접속에서 주로 사용되는 것으로 나타났다"고 보고합니다. 같은 논문은 "{그래서}는 구어체와 문어체에 모두 쓰이는 반면 {따라서}는 주로 문어체에서 사용된다"고도 씁니다[89].
서반석은 `그러므로`가 앞 문장들에서 논리적 과정을 거쳐 새로 도출한 결과('의외적 결과')와 어울린다고 봅니다. `그래서`는 앞 내용에서 어느 정도 예측되는 결과('의내적 결과')와 어울린다고 봅니다[90][91: 114쪽]. 또 "‘따라서’는 논리적인 결과와 아주 잘 어울린다는 점에서 ‘그러므로’와 비슷하다"고 하며[91: 133쪽] 세 낱말이 "‘그래서’와 ‘그러므로, 따라서’로 양분된다"고 결론짓습니다[91: 134쪽]. 다만 저자는 이 구분이 정도의 문제라고 밝힙니다. `그러므로`를 `그래서`로 바꿔도 큰 문제가 없는 예도 있다고 씁니다[91: 115쪽].
김인환은 Sweetser(1990)의 내용, 인식, 화행 세 영역으로 구어 발화를 정량 분석했습니다. 그 결과로 "‘그러면’과, ‘그러니까’는 화행 연결, ‘그래서’는 내용 연결로의 쓰임이 활발함을 확인할 수 있었다"라고 보고합니다. 내용 영역은 뒤 발화가 실제 세계의 사건과 사태를 기술하는 경우이고 인식 영역은 화자의 인식에서 도출한 내용을 말하는 경우입니다[92].
언어 model 연구도 있습니다. 박건숙은 OpenAI API로 GPT-4o를 호출해 한국어능력시험 읽기 지문 784개의 빈칸에 들어갈 접속 부사를 고르게 했습니다[93: 770쪽]. GPT-4o는 원문이 `그래서`인 지문 255개 가운데 78개(30.59%)를 틀렸습니다[93: 774쪽]. 이 실험은 글을 쓰게 한 과제가 아니라 빈칸을 채우게 한 과제였습니다. 박건숙은 Claude를 시험하지 않았습니다.

**접속 부사를 고르는 기준은 이 repository가 정한 규칙입니다.** 앞의 일 때문에 뒤의 일이 일어났으면 `그래서`를 씁니다. 앞에서 밝힌 사실을 근거로 판단, 권고, 결론, 독자가 할 일을 이끌어 내면 `따라서`나 `그러므로`를 씁니다. 이 규칙은 사전 규범이 아니라 위 연구에서 관찰한 경향을 옮긴 것입니다.

**말뭉치에서 `그래서`는 구어에 많이 나오고 `따라서`와 `그러므로`는 문어에 많이 나옵니다.** 전영옥은 세종 구어 전사 말뭉치 201,255어절과 세종 문어 말뭉치 8,844,080어절을 비교했습니다[94: 228쪽]. 1000어절당 빈도는 `그래서`가 구어 6.16, 문어 0.65입니다. `따라서`는 구어 0.05, 문어 0.61입니다. `그러므로`는 구어 0.005, 문어 0.27이고 `그러니까`는 구어 6.12, 문어 0.13입니다[94: 228-230쪽].

**결론의 근거는 결론 바로 앞에 둡니다.** 접속 부사가 받는 범위는 바로 앞 문장에 고정되지 않습니다. 전영옥은 `그러나`가 구어와 문어에서 모두 "단락과 단락의 접속 기능을 가지는 점에서 공통적"이라고 봅니다[94: 233쪽]. 안정아와 남경완은 초등학생 일기에서 접속 부사가 문장뿐 아니라 단락을 잇는 기능도 한다고 보고합니다[97]. 김인환은 접속 부사가 대신 가리키는 대상이 앞 발화에 국한될 때와 언어 맥락이나 상황 맥락으로 넓어질 때를 나눠 봅니다[92]. 서반석은 앞의 세 문장을 모두 근거로 받아 `그러므로`로 결론을 이끄는 예를 듭니다. 예문은 "견우와 직녀는 식중독에 걸렸고, 몽룡은 식중독에 걸리지 않았다. 견우는 김밥과 우유를 먹었고, 직녀는 빵과 우유를 먹었다. 몽룡은 김밥과 빵을 먹었다. 그러므로 식중독의 원인은 우유이다."입니다[91: 113쪽]. 이처럼 접속 부사가 받는 범위는 문맥으로 정해집니다. 이 repository는 결론 바로 앞에 다른 일의 이유가 놓이면 독자가 그 이유를 결론의 근거로 읽을 수 있다고 봅니다.

그래서 skill에는 효과, 성능, 사용량, 비용 같은 지표를 구하는 일을 `측정하다`로 쓰라는 지시가 들어 있습니다. 검사기는 기본 규칙에서 이런 낱말이 목적어인 `재다`를 경고로 알립니다. `build 시간을 쟀습니다`처럼 도구로 재는 시간과 길이는 그대로 둡니다. 지표를 `측정하다`로 쓰는 것은 이 repository의 규칙입니다.

**영어 전치사구와 비유를 낱말 그대로 옮기지 않습니다.** 사용자는 Claude가 `코드 밖에서 만든`, `어떤 모양으로 할지`라고 쓴 답변을 보았다고 알려 왔습니다. `created outside of code`와 `what shape ... takes`를 낱말 그대로 옮긴 말입니다. 두 표현이 함께 든 영어 문장을 한국어로 옮기라는 요청을 여섯 번 보냈습니다. 이 도구를 설치하지 않은 프로젝트에서 세 번, 설치한 프로젝트에서 세 번 보냈습니다. Claude는 여섯 번 모두 `코드 밖에서 만든`, `코드 밖에서 생성된`처럼 `코드 밖에서`를 썼습니다. 이 도구를 설치한 session의 답변에는 run을 옮긴 `돌다`(`check가 돌고 있습니다`, `CI가 다시 돕니다`), test를 옮긴 `시험`(`시험용 APK`), shape를 옮긴 `모양`(`응답 모양`), outside를 옮긴 `바깥`(`바깥 접속`)도 여러 번 나왔습니다. `돕니다`는 `돕다`를 떠올리게 해 뜻이 헷갈리기도 합니다.
그래서 skill에는 누가 무엇을 했는지와 실제로 가리키는 대상을 쓰라는 지시와 예시가 들어 있습니다. 검사기는 기본 규칙에서 `응답 모양`과 `바깥 접속`을 오류로 잡습니다. `코드 밖에서`, `어떤 모양으로`, `돌고 있`, `돕니다`, `시험용`은 정상 문장에도 나올 수 있어 경고로만 알립니다. 한국 개발자가 흔히 쓰는 `test를 돌리다`는 그대로 둡니다. 영어 전치사구와 비유를 낱말 그대로 옮기지 않는 것은 이 repository의 규칙입니다.

**영어 `Why` 제목과 항목 이름을 `왜` 하나로 옮기지 않습니다.** 사용자는 Claude가 영어 `Why`를 `왜`로 옮긴 제목을 자주 쓴다고 알려 왔고 이런 제목을 `문제 및 원인`처럼 쓰라고 했습니다. 사용자가 본 실제 제목은 받지 못했습니다. 표준국어대사전은 `왜2`를 '무슨 까닭으로. 또는 어째서.'라는 뜻의 부사로 풀이합니다[37]. 이 repository는 제목에 이 부사 하나만 두면 그 절이 이유를 다룬다는 것만 드러난다고 봅니다. 무엇이 문제였고 원인이 무엇인지, 어떤 배경에서 바꿨는지는 드러나지 않습니다. 우아한형제들 공통시스템개발팀은 MR template에 `해결하려는 문제가 무엇인가요?`와 `어떻게 해결했나요?` 항목을 두었습니다[100]. 이 template은 항목 이름에 다룰 내용이 드러나는 예일 뿐입니다. 이 template을 소개한 글은 `Why`를 피하라고 말하지 않습니다.
그래서 skill에는 제목과 항목 이름을 `왜` 하나로 짓지 말라는 지시가 들어 있습니다. PR 설명, commit 메시지, 문서, 답변에서는 `## 왜`, `**왜:**`, `왜:` 대신 그 절이나 항목에 담은 내용이 드러나는 이름을 붙이게 합니다. Skill은 bug를 고친 PR에는 `## 문제 및 원인`을, 기능을 추가하거나 동작을 바꾼 PR에는 `## 배경`을 예로 듭니다. 제목과 항목 이름을 `왜` 하나로 짓지 않는 것은 이 repository의 규칙입니다. 기본 규칙에서 검사기는 Markdown 제목, 굵은 글씨로 쓴 줄, 쌍점 앞 항목 이름, 표 머리글 칸에 `왜` 하나만 있으면 경고로 알립니다. 팀이 정한 PR template에 `왜`라는 제목이 들어 있을 수도 있어서 오류로 막지는 않습니다.
이 repository는 `## 왜 이런 일이 생기나`, `## 왜 바꿨나`처럼 `왜` 뒤에 다른 말이 붙은 제목은 고칠 대상으로 보지 않습니다. 이런 제목에서는 무슨 일의 이유를 다루는지 드러나기 때문입니다. 검사기는 이런 제목에 경고를 내지 않습니다. Skill도 이런 제목을 고치라고 하지 않습니다. Skill에 넣은 지시로 Claude가 쓰는 제목이 달라지는지는 실제 model로 평가하지 않았습니다.

**빼도 뜻이 같은 말은 지우고 글 자체를 두고 하는 말은 줄입니다.** 국립국어원은 `과반수 이상`을 `과반수`로, `차로 10분 거리에 위치하고 있다`를 `차로 10분 거리에 있다`로 고칩니다[9: 14-15쪽]. 카카오엔터프라이즈는 `인증 메일을 성공적으로 전송했습니다`를 `인증 메일을 전송했습니다`로, `세션 정보는 지속적으로 유지됩니다`를 `세션 정보는 유지됩니다`로 고칩니다[11].
토스는 글 자체를 두고 하는 말을 줄이라고 하면서 이런 말을 세 가지로 나눕니다. 글의 흐름을 알리는 말(`다음으로`, `앞서 설명했듯이`), 쓸데없이 힘을 주는 말(`사실은`, `결론적으로`), 독자의 반응을 끌어내는 말(`아시겠지만`)입니다[10].

**이름을 붙일 때는 한국 독자가 실제로 부르는 말을 씁니다.** 표준국어대사전은 `사본`을 원본을 그대로 베끼거나 사진으로 찍거나 복사해 만든 책이나 서류로 풀이합니다[37: '사본']. 웹사이트를 가리키는 뜻은 없습니다. 운영 server에 올리기 전에 확인하려고 따로 띄운 환경을 Microsoft와 AWS의 한국어 문서는 `스테이징 환경`이라고 부릅니다[101][102]. 국내 회사의 기술 블로그에는 `테스트 서버`, `개발 서버`, `스테이징 환경`이 나옵니다[103][104][105].
영어로 떠오른 개념에 한국어 이름을 붙일 때는 다루는 제품의 한국어 화면과 문서, 법령과 기관 지침, 국내 개발 문서에서 그 말을 본 적이 있는지 따집니다. 이 기준은 이 repository의 규칙입니다. 어디서도 본 적이 없으면 `시험용 사본`처럼 영어 낱말을 하나씩 옮겨 만든 말일 가능성이 큽니다. 한국 독자가 실제로 부르는 이름에 IT 용어가 들어 있으면 개발자가 읽는 글에서는 'IT 용어 표기' 절에 따라 그 용어를 영어 원어로 씁니다. 예를 들어 `스테이징 환경`은 `staging 환경`으로 씁니다.
특정 제품을 말할 때 그 제품의 한국어 화면에 나오는 말을 쓰는 것도 이 repository의 규칙입니다. Extension은 Chrome 화면에 `확장 프로그램`으로, VS Code 화면에 `확장`으로 나옵니다.

**영어는 처음 한 번만 함께 적고 약어는 처음 한 번만 풀어 씁니다.** 쿠버네티스 한글화 팀과 카카오디벨로퍼스는 용어가 처음 나올 때 괄호에 영어를 적고 그 뒤로는 한국어만 씁니다[33][52]. 토스는 약어를 처음 한 번 풀어 쓰고 그 뒤로는 약어만 씁니다[10]. 카카오디벨로퍼스는 처음에 본문에 쓸 용어를 적고 괄호에 약어나 풀어 쓴 말을 덧붙입니다. 그 뒤로는 본문에 적은 용어를 일관되게 씁니다[52].
이 repository는 독자가 이미 아는 말에는 영어를 함께 적지 않습니다. `결제(checkout) 요청`은 `결제 요청`으로 충분합니다.

**한 개념은 한 이름으로 부릅니다.** 토스는 같은 개념을 `추가`, `첨부`, `넣다`처럼 여러 말로 부르지 말라고 합니다[10]. 카카오디벨로퍼스는 한 용어가 한 개념만 나타내게 합니다[52]. 카카오엔터프라이즈는 `오픈빌더`, `봇빌더`, `챗봇빌더`로 섞어 부르던 이름을 `카카오 i 오픈빌더` 하나로 고칩니다[11].

**달러 금액은 숫자 앞에 `$`를 붙여 씁니다.** 2026년 11월 7일 사용자는 README의 `0.095달러`를 보고 달러 금액은 `$`로 써야 한다고 지적했습니다. 평가 script의 집계표가 비용을 `0.095달러`처럼 출력했고 Claude는 이 값을 README와 문서에 그대로 옮겼습니다. Skill에도 금액 표기 규칙이 없었습니다. 이제 평가 script는 `$0.095`처럼 출력하고 skill은 달러 금액을 숫자 앞에 `$`를 붙여 쓰게 합니다. 조사는 `달러`로 읽은 소리에 맞춰 `$0.095가`처럼 씁니다. 검사기는 숫자 바로 뒤나 공백 하나 뒤에 `달러`를 쓴 금액을 파일, commit 메시지, PR과 issue에 올리는 글에서 `currency-notation` 오류로 막고 답변에서는 경고로만 알립니다. 이 표기는 이 repository의 규칙입니다.

## 문장 부호

이 repository는 산문에 가운뎃점, 줄표, en dash, emoji를 쓰지 않기로 정했습니다. 한글 맞춤법은 짝을 이루는 말이나 공통 성분을 줄여 묶은 말에 가운뎃점 대신 쉼표를 쓸 수 있게 하고 문장 중간에 끼어든 말은 쉼표로 감싸는 것을 기본으로 합니다[82]. 끼어든 말 안에 쉼표가 또 있으면 한글 맞춤법은 줄표를 쓰라고 합니다. 이 repository는 줄표를 쓰지 않으므로 그런 문장을 둘로 나눕니다.

Microsoft는 영어 원문이 쌍점이나 쌍반점으로 끝나도 한국어 문장이 `~하세요`나 `~합니다`로 끝나면 마침표를 쓰라고 합니다[1: 30쪽]. 쿠버네티스 한글화 모범 사례도 쌍점을 마침표로 바꾸는 예를 듭니다[33]. MDN은 한글 맞춤법이 정하지 않은 자리에 쓴 쌍점과 쌍반점, 줄표를 마침표로 바꾸라고 권합니다[106].
한글 맞춤법은 쌍점을 `일시: 2014년 10월 9일 10시`처럼 표제 다음에 항목이나 설명을 붙일 때 쓴다고 정하고 문장 끝에 쓰는 용법은 두지 않습니다. 서술, 명령, 청유를 나타내는 문장의 끝에는 마침표를 씁니다[82].

언어 model이 쓴 한국어 에세이에서는 쉼표가 든 문장의 비율이 61%로 사람이 쓴 에세이의 26%보다 두 배 넘게 높았습니다. 언어 model이 쓴 에세이는 연결 어미 가운데 바로 뒤에 쉼표가 붙은 비율도 20%로 사람이 쓴 에세이의 4%보다 훨씬 높았습니다[107].
그래서 검사기는 한 문장의 쉼표 수와 쉼표 사이 길이를 경고로 알립니다. Skill에도 `그리고`, `그러나` 같은 접속 부사 뒤와 `-고`, `-며` 같은 연결 어미 뒤에 쉼표를 습관처럼 찍지 말라는 지시가 들어 있습니다.

- **Release note와 README:** Release note와 업데이트 소식에는 이용자가 겪는 변화와 이용자가 할 일만 씁니다. 사내 issue 번호, 담당자, 내부 원인, test 일정과 test 환경은 쓰지 않습니다. 공개 repository의 README에는 글쓴이의 local 경로와 사내 주소를 쓰지 않습니다. 세 가지 모두 이 repository의 규칙입니다.
- **블로그 글:** 첫 문단에서 문제와 결과를 요약합니다. 그다음 원인, 고친 방법, 결과, 남은 일을 순서대로 쓰고 고친 방법마다 원리를 설명합니다. 이 관례는 이 repository의 규칙입니다. 처음에는 이 관례가 `문제, 원인, 해결, 결과, 남은 과제`처럼 단계 이름을 나열했습니다. 그러자 Claude가 이 낱말을 그대로 제목으로 썼고 `## 해결 1`, `## 해결 2`처럼 번호를 붙였으며 한 문장뿐인 `## 문제` 절도 만들었습니다. 2026년 11월 8일에 사용자가 이 제목을 지적했습니다. 그래서 제목에는 그 절에서 한 일이나 알게 된 것을 쓰고 단계 이름만 쓰거나 번호를 붙인 제목은 쓰지 않게 했습니다. 수치는 메모에 있는 값과 그 값으로 계산한 값만 씁니다. 메모에 없는 결정은 지어내지 않고 메모에 없는 일정과 다음 글은 약속하지 않습니다. 이 두 가지도 이 repository의 규칙입니다. 이 도구를 설치한 프로젝트에 같은 날 개발과 관계없는 블로그 글 요청을 두 번 보냈습니다. 배송 기간을 4일에서 2일로 줄인 과정을 적은 메모를 주고 회사 블로그 글을 써 달라는 요청이며 `test/fixtures/eval/blog.json`에 있습니다. 메모의 남은 과제는 `두 창고에 재고를 어떻게 나눌지 정해야 함`이었습니다. 첫 번째 답변은 첫 문단 끝에 `이 글에서는 배송이 늦었던 이유와 바꾼 방법, 남은 과제를 소개합니다.`라고 썼습니다. 두 번째 답변은 메모에 없는 계획인 `앞으로 지역마다 어떤 상품이 얼마나 주문되는지 살펴보고 두 창고에 재고를 나누는 방법을 정하겠습니다.`를 덧붙였습니다. 그때 skill의 '내용 고르기' 절은 메모에 없는 팀의 계획을 지어내지 말라고 했습니다. 그러나 블로그 글 관례는 메모에 없는 일정과 다음 글만 약속하지 말라고 했고 남은 일을 팀이 어떻게 처리할지는 다루지 않았습니다. 'AI가 자주 쓰는 습관' 절에서 글 자체를 두고 하는 말로 든 예에도 글이 무엇을 다루는지 알리는 문장은 없었습니다. 그래서 블로그 글의 첫 문단에는 이 글이 무엇을 다루는지 알리는 문장을 쓰지 않게 했습니다. 메모에 없으면 팀이 남은 일을 어떻게 처리할 계획인지도 쓰지 않게 했습니다. 다만 비슷한 일을 흔히 어떻게 처리하는지는 일반 지식으로 설명할 수 있게 했습니다. 이 두 지시도 이 repository의 규칙입니다. Skill을 고친 뒤 같은 요청을 다시 두 번 보냈습니다. 두 답변 모두 글이 무엇을 다루는지 알리는 문장과 메모에 없는 팀의 계획을 쓰지 않았고 재고를 어떻게 나눌지는 남은 과제로만 썼습니다.
- **생성 표시:** Commit 메시지와 PR 설명에 `Co-Authored-By: Claude`나 `Generated with [Claude Code]`를 넣지 않는 것은 이 repository의 규칙입니다. 설치 script는 프로젝트 설정(`.claude/settings.json`)의 `attribution`에 `commit`이나 `pr` 값이 없으면 빈 값을 넣어 Claude Code가 두 줄을 붙이지 않게 합니다. 검사기도 두 줄을 오류로 잡습니다.
