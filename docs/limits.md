# 제약

## skill과 output style

- hook은 Claude가 skill을 불렀는지만 확인하고 skill에 적힌 순서를 모두 따랐는지는 확인하지 않습니다. 따라서 남은 문제는 검사기가 찾는 오류와 경고, 검토 model의 지적으로만 드러납니다.
- output style과 skill에는 처음부터 한국어로 생각하라는 지시가 들어 있습니다. Claude가 실제로 어떤 언어로 생각했는지는 이 도구가 확인하지 못합니다. 따라서 지시가 통했는지는 사람이 답변을 읽고 판단해야 합니다.
- skill과 output style에는 독자에게 필요한 내용만 고르고 공개하는 글에 내부 정보와 개인 정보를 넣지 말라는 지시가 들어 있습니다. 검사기는 글에 든 내용이 독자에게 필요한지, 공개해도 되는지 판단하지 못합니다. 검사기는 개발 server 주소나 사람 이름을 오류로 잡지 않으므로 hook도 이런 글을 막지 않습니다.
- 이 도구의 output style은 프로젝트 설정을 읽은 session에만 적용됩니다. 다른 output style을 고른 session과 subagent에는 이 도구의 output style이 적용되지 않습니다.
- hook은 subagent prompt에는 skill을 요구하지 않습니다. 한글이 `writing-skill-min-hangul` 값보다 적게 든 글에도 요구하지 않습니다. 같은 요청에서 skill을 부르지 않았다는 이유로 두 번 막았는데도 Claude가 skill을 부르지 않으면 hook은 그 뒤로 이 이유로는 막지 않습니다.
- skill에는 CLAUDE.md 같은 프로젝트 지침, 기존 문서, 앞선 답변에 든 번역투를 따라 쓰지 말라는 지시가 들어 있습니다. 그러나 이 도구는 그 글에 이미 들어 있는 표현을 고치지 않습니다. 기존 파일을 고칠 때 hook은 이번 편집으로 새로 생긴 오류만 막고 바뀐 문단에 새로 생긴 경고만 알립니다. 따라서 프로젝트 지침과 문서에 남은 번역투와 IT 용어의 한글 표기는 사람이 `node .korean-style/scripts/check-korean.mjs --all` 결과를 보고 고쳐야 합니다.
- 규칙 문서의 IT 용어 키(`banned-transliteration`, `ambiguous-transliteration`, `banned-translation`)를 비우면 검사기는 IT 용어의 한글 음차와 번역어를 잡지 않습니다. 그러나 설치 script는 skill과 output style에서 말투 문구만 바꾸고 작성 agent 파일의 본문은 바꾸지 않으므로 이 세 가지에 든 영어 원어 지시는 그대로 남습니다. 따라서 Claude가 한글 표기를 쓰게 하려면 프로젝트의 `CLAUDE.md`에 IT 용어를 한글로 적으라고 써야 합니다. 작성 agent는 CLAUDE.md를 불러오지 않습니다. 그러므로 작성 agent가 쓰는 글에 한글 표기를 적용하려면 Claude가 이 agent에게 넘기는 메모에도 같은 지시를 적어야 합니다.
- Codex나 Gemini CLI에서는 skill과 output style, 작성 agent, Claude Code hook이 동작하지 않습니다. 이 두 agent가 쓰는 글에는 Git의 `commit-msg` hook이 하는 commit 메시지 검사만 적용됩니다.

## 작성 agent

- hook은 Claude가 `korean-writer` agent를 불렀는지만 확인합니다. 돌려받은 글을 Claude가 그대로 썼는지는 확인하지 않습니다.
- 같은 요청에서 이 agent를 한 번 부르면 그 요청에서 쓰는 다른 글에는 작성 agent도 skill도 요구하지 않습니다. 검사기가 찾은 오류는 그대로 막습니다.
- hook은 파일 전체가 아니라 이번에 쓰는 내용(`Write` 도구의 내용, `Edit` 도구의 새 문자열)에 든 한글 글자 수로 판단합니다. 그래서 긴 문서를 한 번에 200자보다 적게 나눠 고치면 이 agent를 요구하지 않습니다.
- 소스 파일에서는 주석에 든 한글만 계산에 넣습니다. 코드 안 문자열에는 이 agent를 요구하지 않습니다. 질문(`AskUserQuestion`), 계획(`ExitPlanMode`), 파일 설명(`SendUserFile`)에도 요구하지 않습니다.
- `Edit` 도구로 기존 블록 주석의 안쪽 줄만 고치면 새 문자열에 주석 표시가 없습니다. 그래서 hook은 그 줄을 주석으로 알아보지 못하고 이 agent를 요구하지 않습니다.
- 작성 agent에게는 메모에 적힌 사실로만 글을 쓰라고 지시했습니다. 그래서 작업하던 Claude가 메모에서 빠뜨린 사실은 글에서도 빠집니다. 메모에 틀리게 적은 사실은 글에도 틀린 채로 나옵니다.
- 기본 규칙에서는 화면에 나오는 답변을 이 agent에게 맡기지 않습니다. 답변까지 맡기면 작업하던 Claude가 메모를 쓰고 돌려받은 글을 다시 출력해야 하므로 답이 늦어집니다.
- 작성 agent를 거쳐 글을 받는 데 드는 시간과 비용은 이 repository에서 Claude Code 2.1.310을 `claude -p`로 실행해 한 번 측정했습니다. 작업하던 Claude는 Opus 5.5로, 이 agent는 Sonnet 5.5로 실행했고 effort는 둘 다 low였습니다. 작업하던 Claude가 요청에 적힌 한글 593자짜리 메모를 이 agent에게 그대로 넘겼습니다. 한글 555자인 글을 돌려받아 출력하기까지 25.5초가 걸렸습니다. 비용은 두 model을 합쳐 0.22달러였습니다. 작업하던 Claude가 같은 글을 직접 쓸 때 걸리는 시간은 측정하지 않았습니다.
- 이 agent의 도구는 `Read`뿐입니다. Claude Code 2.1.310에서 `Read`를 뺀 session으로 다음 동작을 확인했습니다. subagent에게 쓸 수 있는 도구가 하나도 남지 않으면 Claude Code는 그 subagent를 시작하지 않습니다. 그래서 작업하던 Claude가 `Read`를 쓸 수 없는 session에서는 이 agent도 시작하지 못합니다. 이때 hook은 같은 요청에서 두 번 막은 뒤로는 이 agent를 요구하지 않습니다.
- Claude Code 문서에 따르면 `.claude/agents/` directory를 새로 만들어 첫 agent 파일을 넣었을 때는 Claude Code를 다시 시작해야 그 agent를 불러옵니다. 이 repository에서는 directory가 이미 있었는데도 agent 파일을 추가한 뒤 실행 중이던 session이 이 agent를 바로 찾지 못했습니다. 같은 session에서 나중에는 이 agent를 쓸 수 있게 됐지만 언제 알아보는지는 확인하지 못했습니다. 따라서 설치한 뒤에는 Claude Code를 다시 시작해야 합니다.

## 검토 hook

- 검토 hook은 `claude` 명령으로 검토 model을 부릅니다. hook을 실행하는 shell의 PATH에 `claude` 명령이 있어야 합니다. doctor는 자신을 실행한 shell에서 `claude` 명령을 찾을 수 있는지만 확인합니다. hook이 실행되는 shell의 PATH는 확인하지 않습니다.
- 검토 hook이 검토 model을 부를 때마다 Claude Code 계정의 사용량이 늘어납니다.
- `claude -p`처럼 비대화형으로 실행한 session에서는 Claude Code가 끝날 때 background hook을 멈추므로 검토가 끝나지 않을 수 있습니다.
- 검토 model도 고칠 표현을 놓치거나 자연스러운 문장을 잘못 지적할 수 있습니다. 현재 검토 지시로 검토 model이 예문을 몇 번 지적하는지 측정했습니다. 측정은 2026년 11월 6일에 Claude Code 2.1.310에서 했습니다. 예문 18개를 묶음 3개로 나눠 model마다 묶음을 여섯 번씩 보냈습니다. 기본값인 Sonnet은 번역투 문장을 48번 가운데 34번 지적했고 자연스러운 문장은 60번 가운데 한 번도 잘못 지적하지 않았습니다. 검토 지시에는 이 예문의 문장과 그 문장에서 고칠 표현을 예로 넣지 않았습니다.
- 예문 가운데 세 문장은 사용자가 Claude Code에서 받아 어색하다고 알려 준 문장입니다. Sonnet은 이 가운데 `앞선 항목은 journal 원문에 있습니다`가 든 화면 문구와 `로그인하신 계정과`로 시작하는 화면 문구를 여섯 번 모두 지적했고 `승인을 묻습니다`가 든 답변 문단은 다섯 번 지적했습니다. 그러나 `앞선 기록:`이 든 문장은 한 번도 지적하지 못했고 `오늘(KST)보다 앞선 항목은`이 든 문장은 세 번만 지적했습니다. `코드 밖에서 만든`이 든 commit 메시지는 두 번 지적했지만 그 가운데 한 번은 `코드 밖에서 만든`이 아니라 `보안 그룹`을 `security group`으로 고치라는 지적이었습니다.
- model을 바꿔도 놓치는 문장은 남습니다. Opus도 Sonnet처럼 번역투 문장을 48번 가운데 34번 지적했고 자연스러운 문장은 한 번도 잘못 지적하지 않았습니다. 사용자가 알려 준 세 문장은 여섯 번 모두 지적했지만 `오늘(KST)보다 앞선 항목은`이 든 문장은 한 번도 지적하지 못했습니다. `코드 밖에서 만든`이 든 commit 메시지는 한 번 지적했지만 `코드 밖에서 만든`이 아니라 `보안 그룹`을 고치라는 지적이었습니다. `앞선 기록:`이 든 문장은 세 번 지적했지만 `앞선 기록`을 고치라는 지적은 한 번뿐이었고 나머지 두 번은 같은 줄의 `첫 배포의 보고서`를 고치라는 지적이었습니다. Haiku는 번역투 문장을 32번 지적했지만 자연스러운 문장을 6번 잘못 지적했습니다.
- 검토 지시는 같은 예문으로 측정하면서 고쳤습니다. 검토 model이 자연스러운 예문의 `test를 돌려 보니`와 `Slack 채널`을 잘못 지적한 것을 본 뒤에 검토 지시에 예외 두 가지를 넣었습니다. 하나는 `돌리다`를 지적하지 말라는 예외이고 다른 하나는 제품의 기능과 메뉴 이름을 그 제품 화면에 나오는 대로 두라는 예외입니다. 두 예외 모두 skill에 적힌 기준입니다. 그래도 이 예문에서 잘못 지적하지 않았다고 해서 처음 보는 글에서도 잘못 지적하지 않는다고 볼 수는 없습니다.
- 검토 지시는 검토 hook 코드에 들어 있어 규칙 문서에서 바꿀 수 없습니다. 검토 지시에는 IT 용어를 영어 원어로 쓰라는 기준이 들어 있고 검토 model은 CLAUDE.md를 읽지 않습니다. 따라서 팀이 IT 용어 키를 비우고 CLAUDE.md에 한글 표기를 쓰라고 적어도 검토 model은 한글 표기를 고칠 표현으로 지적할 수 있습니다.
- 답변은 화면에 나온 뒤에 검토하므로 지적받은 표현도 화면에 그대로 남습니다. 답변에 대한 지적은 다음 요청 때 hook이 Claude에게만 알립니다. Claude가 그 지적을 반영했는지는 hook이 확인하지 않습니다.
- 답을 마친 Claude가 검토 알림을 받고 고친 다음 다시 답을 마칠 때는 검토하지 않습니다. 그래서 이때 고친 글이 다시 어색해도 검토 hook은 알리지 않습니다.
- `reviewer-max-hangul`을 넘어 보내지 않은 조각은 검토하지 않습니다.
- 검토 hook은 Codex와 Gemini CLI에는 적용되지 않습니다.
- 검토 hook이 Windows에서 동작하는지는 확인하지 않았습니다.
- subagent가 끝난 뒤 나온 지적을 Claude Code가 어느 session의 Claude에게 전달하는지는 확인하지 않았습니다.

## 검사기

- 검사기는 규칙 문서에 적힌 형태만 찾습니다. 서술어 하나에 정보를 몰아넣은 문장, 무엇을 가리키는지 흐린 지시어, 영어 문장과 낱말 단위로 맞아떨어지는 문장처럼 목록으로 정할 수 없는 문제는 잡지 못합니다. 항목 이름에 할 일을 몰아넣고 콜론 뒤에 누가 하는지만 쓴 목록도 잡지 못합니다. 프로그램이 하는 일과 Claude가 할 일을 행위자 없이 이은 문장도 잡지 못합니다. 이런 문제는 Claude가 skill을 따라 쓰면서 스스로 피해야 합니다. 이 도구 repository에서는 commit하기 전에 `korean-reviewer` agent로 한 번 더 검토합니다.
- 검사기는 말투마다 정해 둔 어미만 찾습니다. 합니다체 프로젝트에서는 `~세요`, `~어요` 같은 해요체 어미를 찾고 해요체 프로젝트에서는 `~니다`로 끝나는 어미를 찾습니다. 그래서 `~한다` 같은 해라체와 반말은 잡지 못합니다. 다만 답변에서는 `확인해라`, `확인해줘`처럼 `imperative-endings`에 적어 둔 명령 어미를 따로 잡습니다. 합니다체 프로젝트에서도 `~네요`, `~까요`, `~죠`처럼 정해 둔 목록에 없는 해요체 어미는 잡지 못합니다. `돼요`나 `봐요`처럼 어간과 합쳐진 해요체 어미도 일부 잡지 못합니다. 해요체 프로젝트에서는 `~해 주십시오`와 `~습니까`를 잡지 못합니다. 검사기가 잡지 못하는 어미는 Claude가 output style과 skill을 따라 스스로 피해야 합니다.
- 검사기는 글 내용을 보고 일반 독자가 읽는 글인지 판단하지 못합니다. `general-reader-globs`에 적은 경로의 파일과 `<!-- korean-style: general-reader -->` 줄이 든 문서만 일반 독자가 읽는 글로 봅니다. 이 줄은 문서 파일에만 쓸 수 있고 파일 전체에 적용되므로 문서의 일부만 일반 독자가 읽는 글로 정할 수는 없습니다. 경로가 `general-reader-globs`에 들지 않고 이 줄도 없는 이용자 공지에 `서버`나 `로그인` 같은 한글 표기를 쓰면 검사기가 오류로 보고하므로 hook이 쓰기를 막습니다.
- 기본 규칙에서는 `chat-advisory-rules`에 `transliteration`이 들어 있으므로 검사기는 답변과 도구에 넘기는 글에 쓴 IT 용어의 한글 음차를 경고로만 알립니다. 도구에 넘기는 글은 사용자에게 묻는 질문, 계획, 파일 설명, agent에게 주는 prompt입니다. hook은 경고 때문에 막지 않으므로 Stop hook은 한글 음차 때문에 답변을 다시 쓰게 하지 않고 PreToolUse hook도 이런 도구 호출을 막지 않습니다. 이런 글에서도 막으려면 `chat-advisory-rules` 값을 비웁니다.
- 검사기는 IT 용어 표에 적은 말만 잡습니다. `훅`, `스킬`, `이슈`, `리뷰`처럼 일반 뜻으로도 흔히 쓰는 음차는 `ambiguous-transliteration` 경고로만 알립니다. `저장소`, `배포`, `병합`, `분기` 같은 번역어도 `loose-translation` 경고로만 알립니다. `통합테스트`처럼 앞말에 붙여 쓴 합성어와 `테스트케이스`처럼 뒤에 다른 낱말을 붙여 쓴 합성어도 잡지 않습니다.
- 영어를 낱말 단위로 옮겨 만든 말은 규칙 문서에 적은 말만 잡습니다. 이 가운데 오류로 막는 말은 `calques`에 적은 말뿐입니다. 기본 규칙의 `calques`에는 `비멱등`, `미추적`, `반랙`, `전랙`, `응답 모양`, `바깥 접속`만 들어 있습니다. `코드 밖에서`, `어떤 모양으로`, run을 옮긴 `돌고 있`, test를 옮긴 `시험용`은 정상 문장에도 나올 수 있습니다. 따라서 기본 규칙에서는 이런 말을 `translationese-patterns`에 넣어 경고만 나오게 했습니다. 목록에 없는 말을 막으려면 `calques`에 그 말과 대신 쓸 표현을 추가합니다. `calques`에 적은 말은 코드 블록, 인라인 코드, 같은 줄에서 닫은 따옴표 안에 쓰면 잡지 않습니다. 앞에 한글이 붙어 있으면 `POST는비멱등이라`처럼 띄어 쓰지 않은 경우에도 다른 낱말의 일부로 보고 잡지 않습니다.
- 검사기는 항목을 새로 넣는 일을 `더하다`로 쓴 문장 가운데 목적어가 영어 낱말이거나 `object-verbs`에 적은 낱말인 문장만 경고로 알립니다. `저장소도 더할까요`처럼 목적어 뒤에 `을`, `를`, `은`, `는`이 아닌 조사를 쓴 문장은 잡지 못합니다. 영어 목적어는 `을`, `를`이 붙을 때만 잡습니다. 목록에 없는 낱말이 목적어인 문장과 `통합테스트를`처럼 목록의 낱말 앞에 한글을 붙여 쓴 문장도 잡지 못합니다. `사과 세 개에 두 개를 더하면`처럼 수를 합치는 문장도 목적어가 목록에 든 낱말이면 경고가 나옵니다. 목록에 든 낱말에 `은`, `는`을 붙여 주어로 쓴 문장에도 경고가 나올 수 있습니다.
- 검사기는 지표를 구하는 일을 `재다`로 쓴 문장도 `더하다`를 쓴 문장과 같은 방식으로 찾습니다. `효과`, `성능`, `비용`처럼 목록에 든 낱말이 목적어일 때만 경고로 알립니다. 개수를 구하는 일을 `세다`로 쓴 문장은 `수`, `개수`, `글자`, `항목`처럼 목록에 든 낱말이 목적어일 때와 `센 값`처럼 쓸 때만 경고로 알립니다. hook은 경고 때문에 답변을 다시 쓰게 하지 않습니다. 따라서 답변에서는 Claude가 skill을 따라 스스로 고쳐 써야 합니다. Claude는 항목을 새로 넣는 일을 `추가하다`로, 지표를 구하는 일을 `측정하다`로, 개수를 구하는 일을 문맥에 따라 `집계하다`, `계산하다`, `확인하다`로 써야 합니다.
- 기본 규칙에서 검사기는 제목, 굵은 글씨로 쓴 줄, 콜론 앞 항목 이름, 표 머리글 칸에 `왜` 하나만 있을 때만 경고로 알립니다. `## 왜 바꿨나`처럼 `왜` 뒤에 말을 붙인 제목에는 경고가 나오지 않습니다. hook은 경고 때문에 답변을 다시 쓰게 하지 않습니다. 따라서 답변에서는 Claude가 skill을 따라 `왜` 하나만 쓴 제목과 항목 이름을 스스로 고쳐 써야 합니다.
- 한자어와 구어 표현 규칙은 `hanja-words`와 `colloquial-words`에 적은 말만 잡습니다. 기본값에는 `좀`과 접속 부사 `그러니까`가 없으므로 이 두 말은 잡지 않습니다. 검사기는 관형사 `본`을 문장 첫머리에 홀로 쓴 경우만 잡으므로 `이번 변경은 본 PR에서 다룹니다`처럼 문장 중간에 쓴 `본`은 잡지 못합니다. `타`와 `동`도 뒤에 조사나 어미 없이 홀로 쓴 경우만 잡습니다.
- 기본 규칙에서 접속 부사 규칙이 경고로 알리는 경우는 하나뿐입니다. 같은 문단에서 `때문입니다`처럼 `reason-endings`에 적은 말로 끝난 문장 바로 다음 문장이 `그래서`로 시작하는 경우입니다. 그 밖의 자리에서 `그래서`와 `따라서`를 바꿔 쓴 문장은 잡지 못합니다. 앞 문장의 일 때문에 뒤 문장의 일이 일어나 `그래서`가 맞는 글에도 같은 경고가 나옵니다.
- 번역투, 쉼표, 길이, 빈도 규칙은 경고로만 보고합니다. IT 용어 표의 `ambiguous-transliteration`과 `loose-translation`, 한자어와 구어 표현, 접속 부사 규칙도 경고로만 보고합니다. 경고가 나온 표현도 문맥에 맞으면 그대로 두어도 됩니다. CLI에 `--strict`를 붙이면 경고만 있어도 실패로 끝납니다.
- 말투와 표기 규칙 위반을 오류로 나눈 것은 프로젝트 정책입니다. 고유명사에 예외가 필요하면 규칙을 고칩니다.
- 같은 줄에서 닫은 큰따옴표, 한글이 든 작은따옴표, 낫표(`「」`, `『』`), 인라인 코드 안은 말투를 검사하지 않습니다. 코드 블록 안에서도 말투, 금지 문자(emoji 제외), 금지 호칭, 외래어 표기, 오타, 생성 표시는 오류로 잡습니다. 그래서 다른 말투로 쓴 글을 답변의 코드 블록에 옮기면 Stop hook이 다시 쓰라고 요구합니다.
- 문서에서 `<!-- korean-style-quote -->` 줄과 `<!-- /korean-style-quote -->` 줄 사이에 넣은 글은 검사하지 않습니다. 답변과 commit 메시지에서는 이 사이도 검사합니다.
- 지원하는 확장자의 소스 파일에서는 주석만 검사합니다. 코드 안의 문자열과 지원하지 않는 확장자의 파일은 검사하지 않습니다. hook과 전체 검사는 프로젝트 밖 경로를 건너뜁니다.
- 전체 검사는 점(`.`)으로 시작하는 directory와 제외 경로를 건너뜁니다.

## hook

- Stop hook은 답변이 화면에 나온 뒤에 실행되므로 이미 나온 답변을 되돌리지 못합니다. 그래서 첫 답변과 다시 쓴 답변이 함께 보입니다. 다시 쓴 답변은 검사하지 않으므로 고치지 못한 오류나 다시 쓰면서 생긴 오류는 그대로 남습니다.
- Claude Code가 마지막 답변을 넘겨 주면 Stop hook은 그 답변만 검사합니다. 이때 Claude가 도구를 부르는 사이에 쓴 진행 보고는 검사기가 검사하지 않으므로 진행 보고에 든 오류는 그대로 남습니다. 검토 hook은 진행 보고도 검토 model에게 보내지만 이미 화면에 나온 글은 고치지 못합니다.
- 설치 script가 `CLAUDE_CODE_THINKING_DISPLAY_UPDATES=0`을 넣으면 server가 요약한 문장이 화면에 나오지 않을 뿐이고 Claude가 쓴 원래 진행 보고가 대신 나오지는 않습니다. 따라서 server가 요약 대상으로 고른 진행 보고는 화면에 나오지 않습니다. 이 동작은 Claude Code 2.1.310에서 확인했습니다. 다른 버전에서는 환경 변수 이름이나 동작이 다를 수 있습니다.
- 사용자 설정에서 `showThinkingSummaries`를 켜면 Claude Code는 `CLAUDE_CODE_THINKING_DISPLAY_UPDATES` 값과 관계없이 server에 thinking 요약을 요청합니다. 이때 화면에 나오는 요약도 skill과 검사기를 거치지 않습니다.
- 예전 버전의 Claude Code는 Stop hook에 마지막 답변을 넘기지 않습니다. 이때 hook은 transcript를 읽으므로 hook이 실행되는 시점까지 기록된 답변만 검사합니다.
- 기존 파일을 고칠 때 PreToolUse hook은 이번 편집으로 새로 생긴 오류만 막고 파일에 원래 있던 오류는 막지 않습니다. 다만 NotebookEdit 도구로 셀을 고칠 때는 바뀌기 전 셀과 비교하지 않으므로 그 셀에 원래 있던 오류도 막습니다. 고친 줄에 이미 오류로 잡히던 표현이 있을 때 같은 편집에서 그 표현을 한 번 더 쓰면 새로 쓴 표현도 막지 못합니다. IT 용어 표 규칙처럼 같은 표현을 처음 나온 곳에서 한 번만 보고하는 규칙이 많아 편집 전과 후의 오류 수가 같게 나오기 때문입니다. 예를 들어 `캐시`가 든 줄을 고치면서 같은 편집에서 `캐시`를 한 번 더 쓰면 막지 않습니다.
- hook은 Write, Edit, MultiEdit, NotebookEdit 도구로 바꾼 문단에서 `review-rules`에 든 규칙의 경고만 Claude에게 알립니다. 같은 규칙에 걸린 같은 표현이 바뀌기 전 문단에도 같은 수만큼 있으면 알리지 않습니다. 번역투 구절 규칙과 직역 동사 규칙처럼 같은 표현을 처음 나온 곳에서 한 번만 보고하는 규칙이 있습니다. 이런 규칙에서는 이미 있던 표현을 같은 문단에 한 번 더 써도 알리지 않습니다. NotebookEdit 도구로 셀을 고칠 때는 바뀌기 전 셀과 비교하지 않으므로 원래 있던 경고도 알립니다.
- hook은 shell 명령이 파일에 쓰는 경우 가운데 redirection(`>`, `>>`)과 `tee`, `sed -i`, `perl -i`만 알아봅니다. 이 검사는 보안 장치가 아닙니다. 명령으로 실행한 프로그램이 직접 쓰는 파일은 찾아내지 못합니다.
- hook은 `gh pr`과 `gh issue` 명령의 `--title`, `--body`, `--subject`, `-t`, `-b` 값과 `-F -`나 `--body-file -`로 넘긴 heredoc 본문만 검사합니다. pipe로 넘긴 본문은 읽지 못합니다. `--body-file`로 넘긴 파일과 웹 화면에서 쓴 글은 검사하지 않습니다.
- hook은 shell 문법을 다 해석하지는 못합니다. 변수에 담아 넘긴 메시지나 `$(...)`로 다른 명령의 출력을 넘긴 메시지는 읽지 못합니다. 다만 Claude가 여러 줄 메시지에 쓰는 `"$(cat <<'EOF' ... EOF)"` 형태에서는 heredoc 본문을 읽습니다. commit 메시지는 Git의 `commit-msg` hook이 다시 검사합니다.
- hook을 실행하다 예외가 나면 작업은 계속됩니다. 규칙 문서가 맞는지는 `doctor`와 `gate`로, hook이 연결되었는지는 `doctor`로 확인합니다.
- 일반 편집기로 파일을 고치면 Claude Code hook은 실행되지 않습니다.

## 설정과 설치

- 설치 script는 설정 파일 가운데 프로젝트 설정(`.claude/settings.json`)만 바꿉니다. local 설정, 조직 정책, session option은 프로젝트 설정보다 우선합니다. 따라서 이 가운데 한 곳에서 다른 output style을 고르거나 hook을 끄거나 `attribution` 값이나 `env`의 `CLAUDE_CODE_THINKING_DISPLAY_UPDATES` 값을 바꾸면 이 도구의 설정이 적용되지 않습니다.
- doctor는 프로젝트 설정 파일과 local 설정 파일만 확인합니다. session에 실제로 적용된 설정은 Claude Code의 `/status`로 확인합니다.
- 직접 고친 규칙은 다시 설치해도 바뀌지 않으므로 새로 생긴 `review-rules` 키도 들어가지 않습니다. 이 경우 doctor가 주의 항목으로 표시합니다. `calques`, `object-verbs`, `translationese-headings` 키와 `더하다`를 잡는 `literal-verbs` 항목도 들어가지 않습니다. `chat-advisory-rules`, `ambiguous-transliteration`, `term-exempt`, `general-reader-globs`, `translationese-exempt`, `hanja-words`, `colloquial-words`, `reason-endings`, `result-adverbs` 키도 마찬가지입니다. `banned-transliteration`, `calques`, `translationese-patterns`에 새로 넣은 `커밋`, `반랙`, `코드 밖에서`, `승인을 묻` 같은 항목도 들어가지 않습니다. doctor는 이런 항목이 빠졌다고 알리지 않습니다. 새 기본 규칙으로 바꾸려면 `--force`를 붙여 다시 설치합니다. 그런 다음 설치 script가 `.korean-style/rules.backup-*.md`에 backup한 기존 규칙에서 필요한 내용을 직접 옮겨 옵니다.
- 0.4.1까지의 검사기는 낱말 경계를 보지 않습니다. 그래서 이 검사기가 새 규칙 문서를 읽으면 `블로그`, `머지않아`, `나머지`처럼 표에 적은 음차가 들어 있는 다른 낱말도 오류로 보고합니다. `chat-advisory-rules`, `general-reader-globs`, 일반 독자용 표시 줄도 알아보지 못하므로 답변과 이용자 공지에 쓴 한글 음차도 오류로 봅니다. 0.4.1까지의 PreToolUse hook은 편집한 뒤 파일 전체의 오류를 막으므로 한글 음차가 남은 기존 파일을 고칠 때마다 쓰기를 막습니다. 따라서 새 규칙 문서를 commit하면 팀원도 모두 다시 설치해야 합니다.
- 설치한 프로젝트의 gate는 이 도구 repository의 test를 실행하지 않고 자체 검사, 규칙 문서 검사, 전체 파일 검사만 합니다.
- 자체 검사는 이 도구와 함께 설치한 기본 규칙으로 검사기를 확인하므로 사용자가 규칙 값을 바꿔도 실패하지 않습니다. 실제 답변과 문서는 프로젝트 규칙으로 검사합니다.

## 평가

- 이 도구 repository에서 실제 model로 하는 평가는 정해 둔 요청으로 합니다. 같은 요청이어도 model, effort, cache, server 상태에 따라 답변과 실행 시간이 달라집니다.
- Claude Code는 실행할 때마다 server에서 기능 설정을 받아 오고 이 설정에 따라 system prompt가 바뀔 수 있습니다. 평가 도중 system prompt가 바뀌면 같은 요청을 다시 보내도 앞서 cache에 저장한 입력을 읽지 못해 비용이 줄지 않습니다. `npm run eval -- --summary`는 같은 요청을 다시 보낸 결과가 있으면 처음 보낸 요청과 다시 보낸 요청의 비용을 나눠 보여 줍니다. 평가 도중 system prompt가 바뀌면 이 두 비용의 차이가 작게 나오므로 `--summary`가 보여 주는 표에서 알아챌 수 있습니다.
- 이 도구 repository의 README에 실은 측정 결과는 요청 열두 가지를 보내 얻었습니다. 그 가운데 다섯 가지는 skill 예문과 같은 낱말이나 문장을 씁니다.
