# 설치 전후 예시

README에 실은 측정 결과를 얻으려고 보낸 요청 열두 가지와 받은 답변입니다.

요청 열두 가지를 Claude Opus 5.5(`claude-opus-5-5`)에 보냈습니다. 요청마다 이 도구를 설치한 프로젝트에서 두 번, 이 도구가 없는 프로젝트에서 두 번 보냈습니다. 요청을 보낼 때마다 새 session을 열었습니다.

두 프로젝트는 평가 script가 임시 directory에 새로 만들었습니다. 이 도구가 없는 프로젝트는 빈 directory였습니다. 이 도구를 설치한 프로젝트에도 이 도구 말고는 아무것도 없었습니다. Hook과 skill은 이 도구를 설치한 프로젝트에서 실제로 동작했습니다. 두 프로젝트에서 모두 Claude가 쓸 수 있는 Claude Code 도구는 Skill, Read, Bash뿐이었습니다. Claude Code는 사용자 설정과 MCP server를 불러오지 않았고 이 평가용으로 새로 만든 설정 directory를 썼습니다.

Claude Code 2.1.310에서 effort를 medium으로 두고 2026년 11월 6일(한국 시간)에 실행했습니다. 요청 원문은 [showcase.json](../test/fixtures/eval/showcase.json)에 있습니다.

0.4.1을 release한 뒤 skill, output style, 검사 규칙을 개편했습니다. 이 평가에서는 개편한 버전을 설치했습니다. 개편한 버전은 번역투가 무엇인지 정의하고 Claude가 번역투를 쓰지 않게 합니다. 답변을 포함한 모든 글을 격식 있는 문어체로 쓰게 하고 개발자가 읽는 글에서는 IT 용어를 영어 원어로 쓰게 합니다. 접속 부사도 앞뒤 문장의 관계에 맞게 고르게 합니다. 아래 답변은 평가를 실행할 때 설치한 skill과 output style로 받았습니다. 평가를 실행한 뒤에도 두 파일을 고쳤습니다. 예를 들어 skill의 '용어 표기' 절 마지막 항목을 고쳤습니다. 지금 이 항목은 사용자나 `CLAUDE.md` 같은 프로젝트 지침이 IT 용어를 한글로 적으라고 요구하면 그 요구를 따르라고 합니다. Skill에는 목록에 없는 IT와 공학 용어도 영어로 쓰라는 지시와 사람을 상대로 한 `~에 대한`을 고치라는 지시도 추가했습니다.

작성 agent와 검토 hook도 설치되어 있었지만 이 평가의 답변에는 영향을 주지 않았습니다. Claude가 Agent 도구를 쓸 수 없었고 기본 규칙에서는 답변을 작성 agent에게 맡기지 않으므로 작성 agent는 쓰이지 않았습니다. 검토 hook은 답변에 대한 지적을 같은 session의 다음 요청에서 Claude에게 알립니다. 이 평가는 요청마다 새 session을 열었으므로 검토 hook의 지적이 Claude에게 전해지지 않았습니다.

요청마다 요청 원문과 두 프로젝트의 첫 번째 답변을 싣습니다. Claude가 쓴 답변을 그대로 옮겼습니다. 줄마다 앞에 `>`를 붙여 인용으로 표시했고 code block 밖의 줄에는 줄바꿈이 보이도록 줄 끝에 공백 두 개를 넣었습니다. 그 밖에는 바꾸지 않았습니다. 두 번째 답변은 싣지 않았습니다. 요청마다 붙인 설명은 두 프로젝트에서 받은 답변 네 개를 모두 읽고 썼습니다.

이 도구를 설치한 프로젝트에서 Stop hook이 다시 쓰라고 요구한 답변은 6번 요청의 첫 번째 답변 하나였습니다. 이 문서에는 다시 쓴 답변을 실었습니다. 다시 쓰기 전 답변과 무엇이 다른지는 6번 요청의 설명에 있습니다.

## 1. Chrome 확장 프로그램을 고친 뒤 반영되지 않을 때 할 일 묻기

**요청**

<!-- korean-style-quote -->
> Chrome extension을 만들고 있어. Profile 11 프로필에 개발용으로 올려 두고 테스트하는데, 방금 content script랑 manifest를 고쳤는데도 예전 동작 그대로야. 내가 뭘 하면 되는지 짧게 알려 줘.  
<!-- /korean-style-quote -->

**이 도구가 없는 프로젝트의 첫 번째 답변**

<!-- korean-style-quote -->
> Profile 11 창에서 순서대로 해 보세요.  
>
> 1. **확장 새로고침**: `chrome://extensions` → 해당 확장 카드의 ↻(새로고침) 버튼을 누릅니다. manifest를 바꿨다면 이 단계가 꼭 필요합니다.  
> 2. **테스트 중인 탭 새로고침**: 이미 열려 있던 탭에는 예전 content script가 그대로 남아 있습니다. 확장을 새로고침한 뒤 대상 페이지도 F5로 새로고침하세요.  
> 3. **로드한 폴더 확인**: 카드의 "세부정보"에서 경로를 확인하세요. 빌드 도구(webpack, Vite 등)를 쓰면 `dist/`처럼 빌드 결과 폴더를 로드했을 수 있으니, 다시 빌드했는지 봐야 합니다.  
> 4. **오류 확인**: 카드에 "오류" 버튼이 보이면 눌러 보세요. manifest에 오류가 있으면 새 버전이 적용되지 않을 수 있습니다.  
>
> 그래도 그대로라면 확장을 "삭제"한 뒤 "압축해제된 확장 프로그램을 로드합니다"로 다시 올려 보세요. 거의 확실하게 해결됩니다.  
>
> 추가로, 다른 프로필 창의 `chrome://extensions`에서 새로고침하지 않았는지도 확인하세요. 확장은 프로필마다 따로 설치됩니다.  
<!-- /korean-style-quote -->

**이 도구를 설치한 프로젝트의 첫 번째 답변**

<!-- korean-style-quote -->
> 1. Chrome의 Profile 11 창에서 `chrome://extensions`를 열고 해당 확장 프로그램 카드의 새로고침 아이콘을 눌러 주십시오. 파일을 고쳐도 확장 프로그램을 새로고침해야 manifest와 content script가 다시 로드됩니다.  
> 2. test할 웹 페이지 탭도 새로고침해 주십시오. 이미 열려 있던 탭에는 이전 content script가 그대로 남아 있습니다.  
>
> 이렇게 해도 이전 동작이 그대로이면 두 가지를 확인해 주십시오.  
>
> - 카드에 표시된 로드 경로가 실제로 수정한 directory인지 확인해 주십시오. build를 거치는 프로젝트라면 `dist` 같은 출력 directory를 다시 build해야 변경 사항이 반영됩니다.  
> - 카드의 `오류` 버튼에 manifest 오류가 표시되는지 확인해 주십시오. manifest에 오류가 있으면 새 버전이 로드되지 않습니다. 오류가 없는데도 반영되지 않으면 확장 프로그램을 삭제한 뒤 `압축해제된 확장 프로그램을 로드합니다`로 다시 로드해 주십시오.  
<!-- /korean-style-quote -->

**프로젝트마다 두 번 받은 답변에서 본 것**

- 이 도구가 없는 프로젝트에서 Claude는 두 번 모두 첫 문단에 머리말을 넣었습니다. 첫 번째 답변은 `Profile 11 창에서 순서대로 해 보세요.`라고 썼고 두 번째 답변은 첫 문장 다음에 `아래 순서대로 해 보세요.`를 넣었습니다. 첫 번째 답변은 `누릅니다`, `필요합니다` 같은 합니다체 사이에 `새로고침하세요`, `확인하세요` 같은 해요체를 섞었습니다. 두 번째 답변은 처음부터 끝까지 해요체로 썼고 끝에 `대부분은 1번과 2번만 하면 해결돼요.`라는 말을 덧붙였습니다. 두 번 모두 Chrome 화면의 `확장 프로그램`을 대부분 `확장`으로 줄여 썼습니다. 첫 번째 답변의 `확장 새로고침`, `해당 확장 카드`가 그런 예입니다. 로드한 folder의 경로는 첫 번째 답변이 카드의 "세부정보"에서 확인하라고 맞게 안내했습니다. 두 번째 답변은 `"세부정보 → 소스" 경로`라고 썼으나 한국어 Chrome 화면에서 이 항목 이름은 `소스`가 아니라 `출처`입니다. 두 번 모두 `테스트`, `폴더`, `빌드`처럼 IT 용어를 한글 음차로 적었습니다.
- 이 도구를 설치한 프로젝트에서 Claude는 두 번 모두 합니다체로만 답했고 Chrome 화면에 나오는 `확장 프로그램`이라는 말을 썼습니다. 첫 번째 답변은 머리말 없이 할 일 목록으로 시작했고 `test`, `directory`, `build`를 영어로 썼습니다. 두 번째 답변은 `Chrome의 Profile 11 창에서 아래 순서로 진행해 주십시오.`라는 머리말로 시작했고 `script`, `build`는 영어로 썼지만 `폴더`는 한글 음차로 적었습니다. 두 번 모두 로드한 folder의 경로가 카드에 나온다고 잘못 안내했습니다. 첫 번째 답변은 `카드에 표시된 로드 경로가`, 두 번째 답변은 `확장 프로그램 카드에 표시된 경로가`라고 썼습니다. 두 번째 답변은 `` 카드에 `오류` 버튼이 보이면 manifest를 읽지 못한 것입니다. ``라고도 썼습니다. 현재 Chromium 소스에서 카드의 오류 버튼은 이미 로드한 확장 프로그램에 실행 중 오류나 설치 경고, manifest 경고가 있을 때 나옵니다. Manifest 경고만 있으면 버튼 이름은 `경고`입니다. Manifest를 읽지 못해 로드에 실패하면 카드의 버튼이 아니라 `확장 프로그램을 로드하지 못함` 대화상자에 `매니페스트를 로드할 수 없습니다.`라는 문구가 나옵니다. 첫 번째 답변도 `` 카드의 `오류` 버튼에 manifest 오류가 표시되는지 확인해 주십시오. ``라고 한 다음 `manifest에 오류가 있으면 새 버전이 로드되지 않습니다.`라고 써서 이 두 경우를 섞었습니다.
- 두 프로젝트의 답변 네 개는 모두 확장 프로그램을 먼저 새로고침한 뒤 test하던 탭을 새로고침하라고 순서를 맞게 알려 주었습니다. Chrome 개발 문서도 manifest를 고치면 확장 프로그램을 새로고침하고 content script를 고치면 확장 프로그램과 그 script가 들어가는 웹 페이지를 함께 새로고침하라고 합니다. 네 답변 모두 마지막 방법으로 확장 프로그램을 삭제한 뒤 다시 로드하라고 했고 이때 누를 버튼을 `압축해제된 확장 프로그램을 로드합니다`라고 적었습니다. 현재 Chromium 소스의 한국어 번역에서 이 버튼 이름은 `압축해제된 확장 프로그램 로드`입니다. 한국어 Chrome에서 로드한 folder의 경로는 카드에 나오지 않고 카드의 `세부정보`를 누르면 `출처` 항목 아래에 `로드 위치:`로 나옵니다. Emoji, 가운뎃점, 생성 표시를 넣은 답변은 없었습니다.

> 작업 디렉터리가 비어 있어서 코드나 설정은 확인하지 못했습니다. 아래는 일반적인 점검 순서입니다. "배포 후부터, 가끔" 나는 502는 대개 배포·연결 관리 문제이고, 결제 로직 자체 문제인 경우는 드뭅니다.  
>
> ## 1. 502를 누가 반환하는지 확인  
> 502는 프록시(LB, nginx, ingress, API GW)가 업스트림에서 정상 응답을 받지 못했다는 뜻입니다.  
> - **LB/프록시 로그**에서 502가 난 요청의 upstream 주소, 응답 시간, 에러 메시지를 봅니다.  
>   - nginx 예: `upstream prematurely closed connection`, `connect() failed (111: Connection refused)`, `no live upstreams`  
>   - AWS ALB: `elb_status_code=502`인데 `target_status_code`가 `-`이면 타겟이 연결을 끊은 것입니다.  
> - 같은 시각 **앱 로그**에 그 요청이 아예 없다면 앱에 도달하기 전에 끊긴 겁니다.  
>
> ## 2. 가장 흔한 원인 (확률 높은 순)  
>
> **① Keep-alive 타임아웃 불일치**: "가끔" 502가 나면 1순위입니다.  
> 앱 서버의 idle keep-alive 타임아웃이 LB보다 짧으면, LB가 재사용하려던 연결을 앱이 먼저 닫아서 간헐적으로 502가 납니다.  
> - 규칙: **앱 keep-alive > LB idle timeout** (예: ALB 60s면 앱은 65s)  
> - Node.js: `server.keepAliveTimeout = 65000; server.headersTimeout = 66000;`  
> - gunicorn: `--keep-alive 65`  
>
> **② 롤링 배포 중 graceful shutdown 부재**  
> 배포 시각에 502가 몰린다면 이쪽입니다.  
> - 종료되는 파드/인스턴스가 처리 중인 요청을 끊거나, LB에서 빠지기 전에 죽는 경우입니다.  
> - 확인할 것: SIGTERM 처리, `preStop` sleep(5~15s), `terminationGracePeriodSeconds`, LB deregistration delay  
> - readinessProbe가 없거나 너무 빨리 통과하면, 아직 준비 안 된 새 파드에 트래픽이 들어갑니다.  
>
> **③ 업스트림 타임아웃**  
> 결제 API는 PG사 같은 외부 호출이 느린 경우가 많습니다.  
> - 앱이 PG 응답을 기다리는 동안 프록시 `proxy_read_timeout`이나 LB 타임아웃이 먼저 끝나면 502/504가 납니다.  
> - PG 호출 지연(p99)과 프록시 타임아웃을 비교해 보세요.  
>
> **④ 앱 크래시 / OOM**  
> - `kubectl get pods`의 RESTARTS, `kubectl describe pod`의 `OOMKilled` 여부를 봅니다.  
> - 이번 배포로 메모리 사용량이나 워커 수가 바뀌지 않았는지도 확인하세요.  
>
> **⑤ 이번 배포의 변경사항**  
> - 이전 버전과의 diff에서 서버 설정(포트, 워커, 타임아웃), 의존성 버전, 커넥션 풀 설정, 헬스체크 경로를 확인합니다.  
>
> ## 3. 빠르게 좁히는 방법  
> - **502 발생 시각과 배포 시각을 같이 그려 봅니다.** 배포 직후에만 몰리면 ②, 배포 후에도 계속 산발적이면 ①·③·④입니다.  
> - 특정 인스턴스/파드에서만 나는지 봅니다. 한 곳에서만 나면 그 노드 문제입니다.  
> - 가능하면 이전 버전으로 롤백해서 재현되는지 봅니다. 가장 확실한 분리 방법입니다.  
>
> ## ⚠️ 결제 API라서 꼭 확인할 것  
> 502가 났어도 **실제로 결제가 처리됐을 수 있습니다.** 앱은 PG 승인까지 끝냈는데 응답만 끊긴 경우입니다.  
> - 클라이언트가 재시도하면 이중 결제가 될 수 있으니, 멱등키(idempotency key)를 쓰는지 확인하세요.  
> - 502가 난 요청들과 PG사 승인 내역을 한 번 대조해 보는 걸 권합니다.

Skill은 앞의 사실을 근거로 독자가 할 일을 이끌어 낼 때 `따라서`를 쓰게 합니다. 두 번째 답변은 같은 자리에 `따라서`를 썼습니다. 두 번째 답변은 `502는 앱이 아니라 앞단의 load balancer나 proxy가 upstream에서 정상 응답을 받지 못했을 때 반환합니다.`라고 단정했습니다. RFC 9110은 502를 gateway나 proxy 역할을 하는 server가 반환하는 코드로 정의하므로 외부 결제사를 호출하는 앱도 502를 반환할 수 있습니다. 첫 번째 답변은 앱이 PG 오류를 받아 502로 그대로 돌려주는 경우도 다뤘습니다. 두 번 모두 `load balancer`, `proxy`, `log`, `upstream`, `instance`, `connection`, `timeout`을 영어로 썼습니다. 앱은 첫 번째 답변에서 `app`, 두 번째 답변에서 `앱`으로 적었습니다.
- 두 프로젝트의 답변 네 개는 모두 proxy나 load balancer의 log부터 보라고 했고 502가 난 시각을 deploy 시각과 맞춰 보는 방법, keep-alive timeout, process 재시작 기록을 다뤘습니다. keep-alive timeout 불일치는 네 답변이 모두 다뤘고 deregistration delay는 설치한 프로젝트의 두 번째 답변을 뺀 세 답변이 다뤘습니다. AWS 문서도 이 두 가지를 ALB 502의 원인으로 듭니다. 설치한 프로젝트의 두 답변이 적은 Node.js `keepAliveTimeout` 기본값 5초와 ALB idle timeout 기본값 60초도 Node.js 문서, AWS 문서와 맞습니다.

> Requests over the limit receive a 429 Too Many Requests response.
>
> - Apply IP-based rate limit (10 req/min) to login endpoint
> - Return 429 when the limit is exceeded
> - Add tests for rate limiting behavior
> ```
<!-- /korean-style-quote -->

**이 도구를 설치한 프로젝트의 첫 번째 답변**

<!-- korean-style-quote -->

> feat: login API에 rate limit 추가

## 10. 함수에 한국어 주석 달기

**요청**

<!-- korean-style-quote -->
> 아래 함수에 한국어 주석을 달아 줘. 코드는 바꾸지 마.  
>
> ```js
> function backoffDelay(attempt, base = 200, max = 10000) {
>   const delay = Math.min(max, base * 2 ** attempt);
>   return delay / 2 + Math.random() * (delay / 2);
> }
> ```
<!-- /korean-style-quote -->

**이 도구가 없는 프로젝트의 첫 번째 답변**

<!-- korean-style-quote -->
> ```js
> /**
>  * 재시도 횟수에 따라 지수 백오프(exponential backoff) 대기 시간을 계산한다.
>  * 지터(jitter)를 섞어서 여러 클라이언트가 동시에 재시도하는 현상(thundering herd)을 줄인다.
>  *
>  * @param {number} attempt - 현재 재시도 횟수 (0부터 시작)
>  * @param {number} [base=200] - 기본 대기 시간(ms)
>  * @param {number} [max=10000] - 대기 시간 상한(ms)
>  * @returns {number} 실제로 기다릴 시간(ms). 범위는 [delay/2, delay)
>  */
> function backoffDelay(attempt, base = 200, max = 10000) {
>   // 재시도할 때마다 대기 시간을 두 배로 늘린다 (base * 2^attempt).
>   // 단, max를 넘지 않게 제한한다.
>   const delay = Math.min(max, base * 2 ** attempt);
>
>   // "Equal jitter" 방식: 절반은 고정하고 나머지 절반은 무작위로 정한다.
>   // 최소 대기 시간을 보장하면서 재시도 시점이 서로 겹치지 않게 분산한다.
>   return delay / 2 + Math.random() * (delay / 2);
> }
> ```
>
> 코드는 바꾸지 않았고 주석만 달았습니다.  
>
> 예를 들어 기본값을 쓰면 `attempt`가 0일 때 100~200ms, 3일 때 800~1600ms를 기다립니다. 6 이상이면 `delay`가 상한인 10000ms에 걸려서 5000~10000ms를 기다립니다.  
<!-- /korean-style-quote -->

**이 도구를 설치한 프로젝트의 첫 번째 답변**

<!-- korean-style-quote -->
> ```js
> /**
>  * 재시도 횟수에 따라 지수적으로 늘어나는 대기 시간을 계산합니다.
>  * @param {number} attempt 지금까지 재시도한 횟수입니다.
>  * @param {number} [base=200] 첫 대기 시간의 기준값입니다.
>  * @param {number} [max=10000] 대기 시간의 상한입니다.
>  * @returns {number} delay/2 이상 delay 미만의 무작위 대기 시간입니다.
>  */
> function backoffDelay(attempt, base = 200, max = 10000) {
>   // 대기 시간을 base의 2^attempt배로 늘리고 max를 넘지 않게 제한합니다.
>   const delay = Math.min(max, base * 2 ** attempt);
>   // 절반은 고정하고 나머지 절반은 무작위로 정합니다(equal jitter).
>   // 여러 client가 같은 시각에 한꺼번에 재시도하지 않게 하려는 것입니다.
>   return delay / 2 + Math.random() * (delay / 2);
> }
> ```
>
> `base`와 `max`의 단위는 코드에 정해져 있지 않습니다. 그래서 주석에 ms라고 적지 않았습니다. 호출하는 쪽에서 ms로 쓴다면 `@param` 설명에 단위를 추가해 주십시오.  
<!-- /korean-style-quote -->

**프로젝트마다 두 번 받은 답변에서 본 것**

- 이 도구가 없는 프로젝트에서 Claude는 두 번 모두 주석을 `계산한다`처럼 해라체로 달고 code block 뒤 설명은 합니다체로 썼습니다. 그래서 한 답변 안에서 문장 끝이 바뀌었습니다. 두 번 모두 주석에 `지수 백오프(exponential backoff)`, `지터(jitter)`처럼 같은 뜻을 한글과 영어로 두 번 썼고 코드에 없는 밀리초 단위 `(ms)`도 붙였습니다. 두 번 모두 code block 뒤에 말을 덧붙였습니다. 첫 번째 답변은 `코드는 바꾸지 않았고 주석만 달았습니다.`, 두 번째 답변은 `코드는 그대로 두고 주석만 추가했습니다.`라고 썼습니다. 두 답변 모두 `attempt` 값에 따라 기다리는 시간을 예로 들었습니다. 두 번째 답변은 이 예에 en dash를 썼습니다.
- 이 도구를 설치한 프로젝트에서 Claude는 두 번 모두 주석을 합니다체로만 달았고 `client`를 영어로 썼습니다. 코드에 없는 단위는 넣지 않았습니다. 첫 번째 답변은 code block 뒤에 `` `base`와 `max`의 단위는 코드에 정해져 있지 않습니다. 그래서 주석에 ms라고 적지 않았습니다. ``라는 설명을 덧붙였고 호출하는 쪽에서 ms로 쓰면 `@param` 설명에 단위를 추가하라고 제안했습니다. 두 번째 답변은 code block 밖에 아무 말도 쓰지 않았고 `@returns` 설명에 `단위는 base, max와 같습니다.`라고 적었습니다.
- 두 프로젝트의 답변 네 개는 모두 코드를 바꾸지 않았습니다. 네 답변 모두 대기 시간이 시도마다 두 배로 늘다가 `max`에서 멈춘다는 점과 반환값이 `delay`의 절반 이상 `delay` 미만이라는 점을 코드와 맞게 적었습니다. 이 도구가 없는 프로젝트의 두 답변이 `attempt` 값마다 계산한 대기 시간도 코드와 맞습니다.

## 11. Kubernetes Pod가 Pending인 이유 묻기

**요청**

<!-- korean-style-quote -->
> 쿠버네티스에 새로 배포한 Pod가 계속 Pending이고, 이벤트에 0/3 nodes are available: 3 Insufficient cpu라고 나와. 노드 CPU 사용률은 30%밖에 안 되는데 왜 이래?  
<!-- /korean-style-quote -->

**이 도구가 없는 프로젝트의 첫 번째 답변**

<!-- korean-style-quote -->
> 실제 사용률이 아니라 **requests 합계** 때문입니다. 쿠버네티스 스케줄러는 노드의 실제 CPU 사용률(30%)을 보지 않습니다. 노드의 `Allocatable`에서 이미 배치된 Pod들의 `resources.requests.cpu` 합계를 뺀 값을 보고, 거기에 새 Pod의 request가 들어갈 수 있는지만 판단합니다.  
>
> 예를 들어 4코어 노드에서 Pod들이 `requests: cpu: 1`씩 잡아두고 실제로는 0.3코어만 쓴다고 해봅시다. 사용률은 30%로 나오지만 스케줄러 입장에서는 노드가 이미 꽉 찬 상태입니다.  
>
> ## 확인 방법  
>
> ```bash
> # 1. 노드별 requests 할당 현황 확인 (가장 중요)
> kubectl describe node <노드명> | grep -A 10 "Allocated resources"
> ```
>
> 출력 예:  
> ```
>   Resource  Requests      Limits
>   cpu       3800m (95%)   6 (150%)
> ```
> 여기서 Requests가 90% 이상이면 이게 원인입니다.  
>
> ```bash
> # 2. 새 Pod가 요청하는 CPU 확인
> kubectl get pod <pod명> -o jsonpath='{.spec.containers[*].resources}'
>
> # 3. 노드의 Allocatable 확인 (Capacity보다 작음: kubelet/system 예약분 제외)
> kubectl get nodes -o custom-columns=NAME:.metadata.name,CPU_ALLOC:.status.allocatable.cpu
>
> # 4. 어떤 Pod가 requests를 많이 잡고 있는지 확인
> kubectl get pods -A -o custom-columns=NS:.metadata.namespace,NAME:.metadata.name,CPU_REQ:.spec.containers[*].resources.requests.cpu --field-selector spec.nodeName=<노드명>
> ```
>
> ## 흔한 원인  
>
> 1. **새 Pod의 request가 너무 큼**: 예를 들어 `cpu: 2`를 요청했는데 어느 노드에도 남은 할당 가능량이 2코어가 안 되는 경우입니다.  
> 2. **기존 Pod들의 request가 과하게 잡혀 있음**: 실제로는 100m만 쓰면서 1코어씩 예약해 둔 경우입니다.  
> 3. **LimitRange 기본값**: 네임스페이스에 LimitRange가 있으면 request를 안 적어도 기본 request가 자동으로 붙습니다. `kubectl get limitrange -n <ns>`로 확인하세요.  
> 4. **DaemonSet과 시스템 Pod**: 모니터링, 로깅, CNI 같은 DaemonSet이 노드마다 request를 꽤 차지합니다.  
> 5. **사이드카 / init container**: Istio 사이드카 같은 컨테이너의 request도 합산됩니다. init container는 그중 최댓값이 반영됩니다.  
>
> ## 해결 방법  
>
> - **새 Pod의 request를 실제 사용량에 맞게 줄이기**: 가장 빠른 방법입니다.  
> - **기존 워크로드의 request 조정**: `kubectl top pods`로 실제 사용량을 보고 과하게 잡힌 request를 낮춥니다. VPA를 recommendation 모드로 돌려서 권장값을 받아보는 것도 좋습니다.  
> - **노드 추가 또는 Cluster Autoscaler 사용**: request가 정말 다 필요한 값이라면 용량을 늘려야 합니다.  
> - **limit만 쓰고 request 생략은 주의**: request를 생략하면 request가 limit과 같게 설정되므로 오히려 더 많이 차지합니다.  
>
> 먼저 `kubectl describe node`의 `Allocated resources`와 Pod의 request 값을 확인해 보세요. 출력을 붙여주시면 구체적으로 어디를 줄이면 될지 같이 봐드릴게요.  
<!-- /korean-style-quote -->

**이 도구를 설치한 프로젝트의 첫 번째 답변**

<!-- korean-style-quote -->
> scheduler는 실제 CPU 사용률이 아니라 Pod가 선언한 `resources.requests` 합계를 기준으로 node를 고르기 때문입니다. 실제 사용률이 30%여도 이미 배치된 Pod의 CPU requests 합계가 node의 allocatable CPU에 가까우면 새 Pod는 들어갈 자리가 없습니다. 그래서 `Insufficient cpu`가 발생합니다.  
>
> ## 확인 방법  
>
> node마다 requests가 얼마나 할당되었는지 확인해 주십시오.  
>
> ```bash
> kubectl describe node <node-name> | grep -A 8 "Allocated resources"
> ```
>
> 출력에서 `cpu Requests` 비율이 90~100%에 가까우면 이 경우에 해당합니다. `kubectl top node`가 보여 주는 값은 실제 사용량이므로 scheduling 판단과는 관계가 없습니다.  
>
> 새 Pod가 요청한 CPU도 확인해 주십시오.  
>
> ```bash
> kubectl get pod <pod-name> -o jsonpath='{.spec.containers[*].resources}'
> ```
>
> replica가 여러 개이거나 container가 여러 개이면 requests가 합산됩니다. init container는 가장 큰 값이 기준이 됩니다.  
>
> ## 흔한 원인  
>
> 1. 기존 Pod의 requests가 실제 사용량보다 크게 잡혀 있습니다. 예를 들어 requests는 `1`인데 실제로는 `100m`만 쓰는 경우입니다.  
> 2. 새 Pod의 requests가 node 하나의 남은 allocatable보다 큽니다. requests는 node를 나눠 쓸 수 없으므로 cluster 전체에 여유가 있어도 node 하나에 들어가지 않으면 배치되지 않습니다.  
> 3. namespace에 `LimitRange`가 있으면 requests를 적지 않은 Pod에도 기본 requests가 자동으로 들어갑니다. `kubectl get limitrange -n <namespace>`로 확인할 수 있습니다.  
> 4. DaemonSet(logging, monitoring, CNI 등)과 system Pod가 node마다 requests를 상당히 차지하고 있을 수 있습니다.  
>
> ## 해결 방법  
>
> - 기존 workload와 새 Pod의 CPU requests를 실제 사용량에 맞게 낮춥니다. `kubectl top pod` 결과나 VPA의 권장값을 참고할 수 있습니다.  
> - requests를 낮출 수 없으면 node를 추가하거나 더 큰 instance type으로 바꿉니다. Cluster Autoscaler나 Karpenter를 쓰면 이 경우 node가 자동으로 추가됩니다.  
> - 새 Pod가 꼭 떠야 한다면 `PriorityClass`로 우선순위를 높여 낮은 우선순위 Pod를 밀어내게 할 수도 있습니다.  
>
> requests를 낮출 때는 limits와 함께 보아야 합니다. requests만 지나치게 낮추면 node에 Pod가 과하게 몰려 CPU throttling이 생길 수 있습니다.  
<!-- /korean-style-quote -->

**프로젝트마다 두 번 받은 답변에서 본 것**

- 이 도구가 없는 프로젝트에서 Claude는 두 번 모두 머리말 없이 원인부터 썼습니다. 그러나 두 번 모두 요청에 없던 명령 출력을 지어 넣었습니다. 첫 번째 답변은 `출력 예:`라고 밝히고 `3800m (95%)`가 든 출력을 넣었습니다. 두 번째 답변은 예라는 표시 없이 `#   cpu  3800m (95%)  ← 여기가 꽉 차 있으면 원인 확정`이라는 줄을 code block에 넣었습니다. 첫 번째 답변은 `확인하세요`, 두 번째 답변은 `주의하세요`처럼 두 번 모두 합니다체 사이에 해요체를 섞었습니다. 두 번 모두 끝에는 `kubectl describe node` 출력을 보여 주면 같이 보겠다는 제안을 덧붙였습니다. 두 번 모두 `스케줄러`, `노드`를 한글 음차로 적었습니다. 두 번째 답변은 allocatable이 node의 전체 코어 수보다 작은 경우를 설명하며 `system-reserved, kube-reserved, DaemonSet이 일부를 먼저 가져갑니다`라고 썼습니다. Kubernetes 문서에서 allocatable은 node 용량에서 `kube-reserved`, `system-reserved`, eviction threshold를 뺀 값입니다. DaemonSet의 Pod는 allocatable을 줄이지 않고 allocatable 안에서 requests를 차지하므로 이 설명은 문서와 다릅니다.
- 이 도구를 설치한 프로젝트에서 Claude는 두 번 모두 머리말 없이 원인부터 썼고 합니다체로만 썼습니다. 명령 출력을 지어 넣거나 제안을 덧붙이지 않았습니다. 첫 번째 답변은 `scheduler`, `node`, `scheduling`을 영어로 썼지만 두 번째 답변은 `node`는 영어로, `스케줄러`는 한글 음차로 적었습니다. 검사기는 두 번째 답변의 `request를 더한 값`에 영어 add를 옮긴 동사일 수 있다는 경고를 냈습니다. 이 문장의 `더하다`는 수를 합친다는 뜻이므로 skill 기준으로도 고칠 곳이 아닙니다. 두 답변에는 Kubernetes 문서와 맞지 않는 설명도 있습니다. 첫 번째 답변은 새 Pod가 요청한 CPU를 확인하라고 한 다음 `replica가 여러 개이거나 container가 여러 개이면 requests가 합산됩니다.`라고 썼습니다. Scheduler는 replica를 Pod 하나씩 따로 배치하므로 새 Pod의 requests에 다른 replica의 requests를 합산하지 않습니다. 이미 배치된 replica의 requests는 다른 Pod의 requests처럼 그 node의 할당량에 들어갑니다. 두 번째 답변은 `init container와 sidecar의 request도 합산되므로`라고 썼습니다. 문서에 따르면 init container가 여러 개이면 그 가운데 가장 큰 request가 init container의 기준값이 됩니다. Pod의 실제 기준값은 app container와 sidecar container의 request 합계와 이 init container 기준값 가운데 큰 값입니다. 따라서 sidecar의 request가 합산된다는 부분은 문서와 맞고 init container의 request가 합산된다는 부분은 문서와 다릅니다. 첫 번째 답변의 `init container는 가장 큰 값이 기준이 됩니다.`는 문서와 맞습니다. 또 첫 번째 답변은 `requests만 지나치게 낮추면 node에 Pod가 과하게 몰려 CPU throttling이 생길 수 있습니다.`라고 썼습니다. 문서는 CPU limit을 넘을 때 kernel이 그 container의 실행을 잠시 멈추게 한다고 설명하고 CPU request는 여러 container가 CPU를 다툴 때 CPU 시간을 나누는 가중치라고 설명합니다. 따라서 requests를 낮췄을 때 생기는 일을 throttling이라고 부른 것은 문서의 설명과 다릅니다.
- 두 프로젝트의 답변 네 개는 모두 scheduler가 실제 사용률이 아니라 requests 합계를 보고 Pod를 배치한다고 맞게 설명했습니다. Kubernetes 문서도 node의 실제 CPU 사용량이 낮아도 용량 검사를 통과하지 못하면 scheduler가 Pod를 배치하지 않는다고 합니다. 네 답변 모두 `kubectl describe node`의 `Allocated resources`에서 requests 비율을 보라고 했고 LimitRange 기본값도 확인하라고 했습니다. 이 도구가 없는 프로젝트의 두 답변은 limit만 정하고 request를 생략하면 request가 limit과 같은 값이 된다고 설명했습니다. 이 설명은 Kubernetes 문서와 맞습니다.

## Skill 예문과 겹치는 요청

요청 열두 가지 가운데 1, 3, 4, 7, 12번 요청은 요청 원문이나 요청이 쓰게 하는 글의 구절이 skill 예문의 고칠 문장이나 고친 문장에 그대로 나옵니다. 그래서 요청을 이 다섯 가지와 나머지 일곱 가지로 나눴습니다. 요청마다 겹치는 예문은 다음과 같습니다.

- 1번: `Profile 11에서 확장을 새로고침해 주십시오` → `Chrome의 Profile 11에서 확장 프로그램을 새로고침해 주십시오`
- 3번: `allow`, `make sure`, 수동태를 누가 무엇을 하는지로 풀어 쓰라는 지시와 `This feature allows users to export data` → `이 기능을 사용하면 data를 내보낼 수 있습니다`, `훅` → `hook`, `로컬에서 테스트 후 PR 올릴 것` → `local에서 test한 뒤 PR을 올려 주십시오`
- 4번: `커넥션 풀`, `파이프라인` → `connection pool`, `pipeline`, `이 문서에서는 배포 파이프라인에 대한 개요를 제공합니다` → `이 문서는 deploy pipeline을 간략하게 설명합니다`, `알림이 오도록 alert를 추가합니다` → `알림을 추가합니다`, Slack에 올릴 글 앞에 붙인 머리말을 다룬 예문 `슬랙에 붙여 넣을 수 있게 썼다는 해요체 머리말로 시작해`
- 7번: `이 기능은 사용자가 데이터를 내보내는 것을 허용합니다` → `이 기능을 사용하면 data를 내보낼 수 있습니다`, `세 개의 컴포넌트를 가지고 있습니다` → `component가 세 개입니다`, `설정하는 것이 가능합니다` → `설정할 수 있습니다`, 그대로 둘 표현으로 든 `server로부터 응답을 받지 못했습니다`와 `VPN을 통해 사내망에 접속합니다`
- 12번: `[안내] 결제 서비스 점검 안내` → `[안내] 결제 서비스 점검`, `일시: 10월 24일`, 상투적 문구의 예 `더 안정적인 서비스를 위해`

요청에 든 낱말이 skill의 IT 용어 목록에만 나오거나 요청과 skill 예문이 낱말 하나만 같으면 겹치는 요청으로 보지 않았습니다. 10번과 12번을 뺀 열 가지 요청에 `로그`, `배포`, `테스트`, `로그인` 같은 IT 용어 목록의 낱말이 들어 있어서 이 목록으로는 요청을 나눌 수 없습니다.

이 문서 앞에 적은 기준 가운데 머리말, 덧붙인 말, 요청에 없는 내용 세 가지를 사람이 답변을 읽고 집계했습니다. 한 답변에 같은 항목이 여러 번 나와도 한 번으로 집계했습니다. 머리말은 답변의 첫 문단에서 답변 자체를 소개하거나 이어질 순서를 알리는 문장만 집계했습니다. 요청에 없는 내용은 요청한 글이나 답 안에 넣은 것만 집계했습니다. 요청한 글이나 답 뒤에 덧붙인 말 안에 든 내용은 덧붙인 말로만 집계했습니다.

질문인 1, 6, 11번 요청에서는 답변에 쓴 설명과 확인 방법을 요청에 없는 내용으로 집계하지 않았습니다. 이 세 요청에서는 지어 넣은 명령 출력과 질문에 없던 주제를 다룬 절이나 문단만 집계했고 지어 넣은 명령 출력은 예라고 밝혔는지와 관계없이 집계했습니다. 같은 세 요청에서 덧붙인 말은 답을 마친 뒤 답 전체를 두고 한 말과 정보를 더 주면 더 살펴보겠다는 제안만 집계했습니다. 답변마다 무엇을 집계했는지는 위 요청별 설명에 있습니다.

| 머리말이 있는 답변 | 10개 중 3개 | 10개 중 1개 | 14개 중 4개 | 14개 중 4개 |
| 덧붙인 말이 있는 답변 | 10개 중 5개 | 10개 중 1개 | 14개 중 12개 | 14개 중 5개 |
| 요청에 없는 내용이 있는 답변 | 10개 중 4개 | 10개 중 0개 | 14개 중 11개 | 14개 중 2개 |

Skill 예문과 겹치지 않는 일곱 가지 요청에서도 덧붙인 말과 요청에 없는 내용은 이 도구를 설치한 프로젝트의 답변에서 더 적게 나왔습니다. 그러나 머리말은 두 프로젝트에서 모두 14개 중 4개였습니다. 겹치지 않는 요청에서 이 도구를 설치한 프로젝트의 답변 가운데 머리말이 나온 답변은 5번 요청의 첫 번째 답변, 6번 요청의 두 답변, 8번 요청의 두 번째 답변입니다.

이 도구를 설치한 프로젝트에서 덧붙인 말이 있는 답변 여섯 개 가운데 네 개는 요청에 없어서 넣지 않은 내용을 설명했습니다. 5번 요청의 두 답변, 10번 요청의 첫 번째 답변, 12번 요청의 두 번째 답변입니다. Skill은 고르면서 뺀 내용을 설명하는 문단을 덧붙이지 말라고 합니다.

평가할 때 쓴 skill의 `AI가 자주 쓰는 습관` 절은 머리말을 붙이거나 묻지 않은 제안을 덧붙이거나 요청에 없는 내용을 넣는 일을 어떤 글에서든 하지 말라고 했습니다. 이 절은 `test 목록`, `예시 코드`, `코드를 붙여 주시면 다시 써 드릴게요` 같은 예를 들었습니다. 5번 PR 설명과 8번 review comment에서 이 도구가 없는 프로젝트의 답변에 나온 내용은 이 예와 거의 같습니다. 그리고 5번 PR 설명, 8번 review comment, 9번 commit 메시지는 skill의 글 종류별 관례가 다루는 글입니다. 따라서 겹치지 않는 요청에서 나온 차이도 skill의 다른 지시와 예 때문일 수 있습니다. 두 묶음의 요청이 다섯 가지와 일곱 가지뿐이므로 묶음에 따라 차이의 크기가 다른지는 이 숫자로 말할 수 없습니다.

겹치는 요청에서 이 도구를 설치한 프로젝트의 답변은 skill 예문과 같은 낱말과 짜임을 썼습니다. 1번 요청의 `Chrome의 Profile 11 창에서`와 `확장 프로그램`, 3번 요청의 `local에서`와 `hook`, 4번 요청의 `connection pool`과 `deploy pipeline`, 7번 요청에서 그대로 둔 `원본 서버로부터`, 12번 요청 두 번째 답변의 제목 `[안내] 결제 서비스 점검`이 그런 예입니다. 이 도구가 없는 프로젝트의 답변은 1번 요청에서 `확장`, 3번 요청에서 `로컬에서`와 `훅`을 썼습니다. 이 차이는 skill 예문 때문일 수 있습니다. 겹치지 않는 6번 요청에서도 이 도구를 설치한 프로젝트의 두 답변은 skill 예문 `비멱등 요청` → `멱등하지 않은 요청`에서 고친 표현과 같은 `멱등하지 않으므로`를 썼습니다.

IT 용어 표기의 차이는 겹치는 요청과 겹치지 않는 요청에서 모두 나왔습니다. Skill의 IT 용어 표기 지시와 검사기 규칙은 모든 요청에 적용되므로 이 차이는 예문과 겹치는지로 나눠 볼 수 없습니다.

## 다시 실행하기

아래 명령은 이 문서의 결과를 만든 명령입니다. 앞의 두 명령은 유료 API를 호출합니다. 마지막 명령은 저장한 결과만 집계하므로 API를 호출하지 않습니다. 같은 요청이어도 답변은 실행할 때마다 달라질 수 있고 비용과 시간도 cache와 server 상태에 따라 달라집니다.

```bash
npm run eval -- --run --cases test/fixtures/eval/showcase.json --models claude-opus-5-5 --effort medium --repeat 2 --individual --with-hooks --profiles baseline --out .eval/2026-11-06-baseline
npm run eval -- --run --cases test/fixtures/eval/showcase.json --models claude-opus-5-5 --effort medium --repeat 2 --individual --with-hooks --profiles installed --out .eval/2026-11-06-installed
npm run eval -- --summary .eval/2026-11-06-baseline .eval/2026-11-06-installed
```

README의 설치 전후 비교에 실은 답변은 아래 세 명령 가운데 앞의 두 명령으로 받았습니다. 이 두 명령은 유료 API를 호출합니다. 마지막 명령은 저장한 결과만 집계합니다.

```bash
npm run eval -- --run --cases test/fixtures/eval/readme.json --models claude-opus-5-5 --effort medium --repeat 2 --individual --with-hooks --profiles baseline --out .eval/2026-11-07-readme2-baseline
npm run eval -- --run --cases test/fixtures/eval/readme.json --models claude-opus-5-5 --effort medium --repeat 2 --individual --with-hooks --profiles installed --out .eval/2026-11-08-readme9-installed
npm run eval -- --summary .eval/2026-11-07-readme2-baseline .eval/2026-11-08-readme9-installed
```

README의 설치 전후 비교에 쓴 두 평가도 이 절 뒤쪽에 적은 방법대로 새로 만든 설정 directory에서 실행했습니다. 실행하기 전에 `claude -p`를 두 번 실행해 기능 설정을 받아 두었습니다.

`--with-hooks`를 주면 두 프로젝트에서 모두 Claude가 Skill, Read, Bash를 쓸 수 있고 hook과 skill은 이 도구를 설치한 프로젝트에서 실제로 동작합니다. `--with-hooks`를 빼면 실행 조건이 이 문서와 달라집니다. 이때 평가 script는 `--profiles installed`로 만든 프로젝트에도 이 도구를 설치하지 않고 output style만 넣으며 Claude는 두 프로젝트에서 모두 아무 도구도 쓸 수 없습니다.

`--individual`을 주면 요청마다 새 session을 엽니다. 이 option을 빼면 평가 script는 요청을 모두 묶어 한 번에 보냅니다. `--effort`를 주지 않으면 `low`로 실행합니다. 결과는 `--out`에 준 경로에 저장합니다. 이미 결과가 있는 경로를 주면 실행하지 않고 멈춥니다. 이 repository에서는 결과를 `.eval/` 아래에만 두고 commit하지 않습니다.

`--cases`로 다른 평가 입력을 고를 수 있습니다. 주지 않으면 평가 script는 `cases.json`을 씁니다. 평가 입력은 [test/fixtures/eval/](../test/fixtures/eval/)에 있습니다.

- `blog.json`은 개발과 관계없는 블로그 글 요청 하나를 담은 입력입니다. 배송 기간을 줄인 과정을 적은 메모를 주고 회사 블로그에 올릴 짧은 글을 쓰게 합니다. 이 입력으로는 제목에 그 절의 내용이 드러나는지와 메모에 없는 계획이나 개발 예제가 답변에 들어가는지 봅니다.
- `calque.json`은 한국어로 옮기면 번역투가 나오기 쉬운 영어 문장을 모은 입력이고 번역이 아닌 요청도 세 가지 들어 있습니다. 그 가운데 두 요청은 답변에 영어를 낱말 단위로 옮겨 만든 말이 나오는지 보려고 넣었습니다. 나머지 한 요청에서는 할 일마다 담당자를 적어 둔 영어 메모를 한국어로 정리하게 하고 Claude가 할 일과 담당자를 한 문장에 쓰는지 봅니다.
- `content.json`은 개인정보 처리방침, 업데이트 소식, README, 장애 안내처럼 공개하는 글을 쓰게 하는 입력이고 요청마다 프로젝트 메모나 영어 문단을 함께 줍니다. 이 입력으로는 독자에게 필요 없는 내부 정보와 개인 정보가 답변에 들어가는지 봅니다. `사본`처럼 영어를 낱말 단위로 옮긴 말이 들어가는지도 봅니다. 일반 독자가 읽는 글에 한글로 적어야 할 `page`, `browser`, `cookie` 같은 영어 낱말이 들어가는지도 봅니다.
- `native-verb.json`은 항목을 새로 넣는 일과 지표를 구하는 일을 한국어로 쓰게 하는 입력입니다. 요청에는 `추가`, `측정`이라는 말을 넣지 않았습니다. 이 입력으로는 Claude가 영어 `add`와 `measure`를 `더하다`, `재다`로 옮기는지 봅니다. 수를 합치는 영어 문장을 옮기는 요청도 하나 넣었고 이 요청의 답변에서는 `더하다`나 `합하다`를 쓰고 `추가`를 쓰지 않는지 봅니다.
- `readme.json`은 README의 설치 전후 비교에 쓴 요청 하나를 담은 입력입니다. 메모를 주고 팀 기술 블로그에 올릴 짧은 글을 쓰게 합니다. 이 입력으로는 메모에 없는 내용과 덧붙인 말이 답변에 들어가는지 봅니다.

평가 script는 요청마다 `must`에 적은 낱말이 답변에 없거나 `mustNot`에 적은 표현이 답변에 나오면 제약 위반으로 집계합니다.

이 문서의 결과는 이 평가용으로 새로 만든 설정 directory로 `showcase.json`을 쓰는 앞의 두 명령을 실행해 얻었습니다. 사용자 설정 directory에 든 내용이 요청에 섞이지 않도록 `CLAUDE_CONFIG_DIR` 환경 변수로 설정 directory를 따로 정했습니다. 앞선 평가에서는 새로 만든 설정 directory로 처음 실행했을 때 system prompt가 다음 실행과 달랐습니다. 이 차이는 Claude Code가 server에서 기능 설정을 아직 받지 못해 생긴 것으로 보입니다. 그래서 이번에도 평가하기 전에 `claude -p`를 두 번 실행해 기능 설정을 받아 두었습니다.

`--summary`는 같은 요청을 다시 보낸 결과가 있으면 비용을 처음 보낸 요청과 다시 보낸 요청으로 나눠 보여 줍니다. 같은 요청을 다시 보내면 API가 처음 요청 때 cache에 저장해 둔 입력을 다시 읽으므로 비용이 줄어듭니다.

이번 평가에서 이 도구를 설치한 프로젝트의 답변 하나에 든 평균 비용은 처음 보낸 요청에서 $0.215, 다시 보낸 요청에서 $0.158였습니다. 다시 보냈을 때 비용이 조금만 줄었습니다. 0.3.2 버전을 설치한 지난 평가에서는 $0.123에서 $0.038로 줄었습니다.

실행 기록 파일(`.jsonl`)에는 API 호출마다 cache에 새로 저장한 token 수(`cache_creation_input_tokens`)와 cache에서 읽은 token 수(`cache_read_input_tokens`)가 남습니다. 이 기록을 보면 다시 보낸 요청에서도 skill 본문을 cache에서 읽지 못하고 다시 저장한 요청이 있었습니다. 이런 요청은 모두 처음 보냈을 때나 다시 보냈을 때 Claude가 Skill 도구를 부른 첫 응답에 thinking block이 들어 있었습니다. 처음 보냈을 때와 다시 보냈을 때 모두 첫 응답에 thinking block이 없던 요청은 skill 본문까지 cache에서 읽었습니다.

이번 평가에서는 다시 보낸 요청 가운데 `readme-intro`만 skill 본문을 cache에서 읽었고 나머지 요청은 모두 skill 본문을 다시 저장했습니다. 지난 평가에서는 `ext-reload`, `deploy-502`, `maintenance-notice`만 skill 본문을 다시 저장했습니다.

Skill 본문을 다시 저장한 것은 thinking block이 응답마다 달라서 그 뒤에 오는 skill 본문을 포함한 입력이 처음 요청 때와 달라졌기 때문으로 보입니다. 이 원인은 기록을 보고 추정한 것이며 확인하지는 않았습니다. 지난 평가 뒤로 SKILL.md 파일이 17,011 byte에서 40,202 byte로 길어졌으므로 다시 저장하는 양도 늘었습니다.
